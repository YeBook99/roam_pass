# 요구사항 하나 구현하기

인자: REQ ID (예: `REQ-2.4`). 없으면 `docs/PROGRESS.md`의 첫 번째 미완료 항목을 사용자에게 제안하고 확인받는다.

## 1. 이해 (코드 쓰기 전)
- `docs/GUIDE.md` 에서 해당 ID 표 행과 관련 절(상태 §6, 시나리오 §7, 테스트 §10)을 읽는다.
- `CLAUDE.md` 불변 규칙 중 이 요구사항에 걸리는 것을 골라 사용자에게 2~4줄로 말한다.
  예) "REQ-2.4는 I2(조건부 UPDATE), I4(같은 반영 메서드), I5(event_key) 가 핵심입니다."
- 설계가 GUIDE 와 달라져야 하면 **먼저 사용자에게 이유와 함께 묻고**, 결정되면 `docs/DECISIONS.md` 에 기록한다.

## 2. 테스트 먼저 (정합성 항목은 필수)
- GUIDE §10 의 테스트 이름을 그대로 쓴다. assert 는 **DB 행 수 / 상태 값 / 이력 줄 수** 처럼 구체적으로.
- 동시성: `ExecutorService` + `CountDownLatch`, 스레드 ≥ 10, Testcontainers MySQL.
- 테스트가 실패하는 것을 먼저 확인한다 (가능하면).

## 3. 구현
- 가장 단순한 방법으로. 새 추상화·라이브러리는 사용자 확인 후.
- 외부 호출은 트랜잭션 밖(I1), 상태 전이는 조건부 UPDATE + status_history(I2, I3).
- "왜" 가 필요한 줄에만 한 줄 주석 (인터뷰에서 물어볼 지점).

## 4. 확인
- `cd backend && ./gradlew test --tests '<관련 테스트>'` 실행, 결과를 그대로 보여 준다. 실패면 고친다.
- 화면 작업이면 `npm run build` 또는 실제 실행으로 확인.

## 5. 기록 · 커밋
- `docs/PROGRESS.md` 체크 (`- [x]`). 포기/축소했으면 `- [~] … — 사유`.
- 결정이 있었다면 `docs/DECISIONS.md` 에 3~5줄.
- 사용자가 내 제안을 고쳤다면 `docs/LEARNING_LOG.md` "AI가 틀린 순간 (후보)"에 사실만 짧게.
- `commit` 스킬 규칙으로 기능 단위 커밋 (스키마 / 기능 / 테스트 분리 가능).

## 6. 마무리 보고
- 무엇을 했는지 3줄, 실행한 테스트와 결과, 알려진 한계 1~2개.
- "`/explain <핵심 클래스>` 로 설명 연습을 해 보시겠어요?" 제안.

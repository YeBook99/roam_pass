# 11. 테스트 전략

> 2.5-5: 커버리지는 보지 않는다. **중복 통지·중복 콜백 동시성 테스트**와 **"결제됐는데 발급 실패" 시나리오 테스트**는 꼭 있어야 하고, **만료일(UTC→KST) 계산 테스트**를 권장한다.
> 2.7: 양보다 **"무엇을 검증했는지"**. `assertTrue(true)` 같은 테스트는 감점이다.

도구 설명은 [L4 동시성 테스트 도구](learn/L4_동시성_테스트_도구.md)를 본다.

## 1. 원칙

1. **진짜 PostgreSQL로 테스트한다**(Testcontainers). 중복 방지를 DB 제약으로 했으므로 DB를 가짜로 바꾸면 검증할 대상이 사라진다
2. **관찰 가능한 결과를 센다.** "예외가 안 났다"가 아니라 "payment 행이 1개다", "이력이 1줄이다", "PG 취소 호출이 1번이다"를 검증한다
3. **동시에** 보낸다. 순서대로 20번 보내는 테스트는 동시성 테스트가 아니다. `CountDownLatch`로 출발선을 맞춘다
4. **시간은 주입한다**(`Clock`). 만료와 재시도 간격 테스트에서 실제로 10분을 기다리지 않는다
5. 모의 PG와 공급사의 지연, 실패, 중복은 **설정으로 조절**한다. 테스트마다 원하는 상황을 만든다

## 2. 필수 테스트 (과제 요구)

### T1. `PaymentWebhookConcurrencyTest` — 중복 결제 통지
- **Given** PENDING 주문 1개, READY 결제 1개
- **When** 같은 승인 웹훅 20개와 승인 API 응답 처리 1개를 21개 스레드에서 **동시에** 실행
- **Then**
  - `payment` 중 APPROVED는 정확히 1행
  - 주문 상태는 PAID
  - `status_history`의 `PENDING→PAID`는 정확히 1행
  - `callback_log`에서 해당 event_key는 1행
  - 발급 요청(모의 공급사 `POST /orders` 수신 수)은 1회 (Awaitility로 대기)
  - 반환값 집계: PROCESSED 1, DUPLICATE 20

### T2. `SupplierCallbackConcurrencyTest` — 중복 발급 콜백
- **Given** ISSUING 주문, supplierOrderNo 저장됨
- **When** 서명이 올바른 같은 발급 콜백 20개를 **동시에** 전송
- **Then** `sim_profile` 1행, 주문 ISSUED, `ISSUING→ISSUED` 이력 1행
- **추가 케이스**
  - 서명이 틀린 콜백은 401이고, `sim_profile`은 0행이며, `callback_log`에 SIGNATURE_INVALID 1행
  - 같은 supplierOrderNo에 ICCID가 다른 콜백이 오면 기존 프로필을 유지하고 CONFLICT를 기록

### T3. `IssueFailureCompensationTest` — 결제됐는데 발급 실패
- **케이스 A (자동 환불 성공)**
  - Given: 공급사 `issueFailRate=1.0`
  - When: 결제 확정 → 발급 시도 → 시계를 2분씩 전진하며 스케줄러 실행 × 3
  - Then: 주문이 `ISSUE_FAILED → REFUNDING → REFUNDED`, 결제 CANCELED, 모의 PG 취소 수신 1회, 이력에 SYSTEM actor
- **케이스 B (환불도 실패)**
  - Given: 추가로 PG `cancelFailRate=1.0`
  - Then: 환불 시도 3회 후 `REFUND_FAILED`이고, `refund_attempt.attempt_count = 3`이며, `/api/admin/anomalies`에 REFUND_FAILED로 노출. **4번째 시도는 일어나지 않음**(무한 재시도 금지 검증)
- **케이스 C (콜백 미도착)**
  - Given: 공급사 `callbackDropRate=1.0`
  - Then: 콜백 타임아웃 재시도 3회 → ISSUE_FAILED → 환불 (인터뷰 I4 증명)

### T4. `ExpiryCalculatorTest` — UTC → KST 만료
| 입력 activatedAt (UTC) | days | 기대 expiresAt (UTC) | 기대 KST 표시 |
|---|---|---|---|
| 2026-05-01T15:20:00Z | 7 | 2026-05-08T15:20:00Z | 2026-05-09 00:20 |
| 2026-05-01T14:59:59Z | 1 | 2026-05-02T14:59:59Z | 2026-05-02 23:59:59 |
| 2026-12-31T16:00:00Z | 3 | 2027-01-03T16:00:00Z | 2027-01-04 01:00 (연도 넘김) |
- 추가: JVM 기본 타임존을 `America/New_York`으로 바꿔도 결과가 같은지 확인(서버 타임존 의존 방지)

## 3. 구조 규칙 테스트와 나머지 흐름 확인

- **`ArchitectureTest`(ArchUnit)**: 레이어드 구조 규칙(계층 접근, 다른 기능 Repository 사용 금지, 기능 사이 순환 금지, `global`의 기능 의존 금지, `@Transactional` 위치, 필드 주입 금지)을 빌드마다 검사한다(ADR-15). 실패하면 테스트가 아니라 코드를 고친다
- **테스트 코드는 과제 필수(T1~T3)와 `ArchitectureTest`만 둔다.** 설명할 코드를 늘리지 않으려는 결정이다. 아래 표의 흐름은 테스트 코드 대신 docker compose로 띄워 직접 호출해 확인하고, 그 결과를 커밋 메시지 `[검증]`에 남긴다
- 아래 표는 처음 세운 "권장 테스트" 목록이다. 시간이 남으면 위에서부터 테스트로 옮길 후보다

| 후보 (지금은 수동 확인) | 검증 |
|---|---|
| `AdminRefundConcurrencyTest` | 운영자 2명이 동시에 환불 → PG 취소 1회, 한 명은 거절, `admin_action` 2행 |
| `PaymentAmountMismatchTest` | 웹훅 금액 -1000 → 주문 PENDING 유지, AMOUNT_MISMATCH 기록 |
| `PaymentIdempotencyKeyTest` | 같은 키로 결제 요청 5회 동시 → payment 1행, 모의 PG 승인 수신 1회 |
| `PaymentTimeoutReconcileTest` | PG 응답 지연(타임아웃) → READY 유지 → 대사 스케줄러 → PAID |
| `OrderExpireRaceTest` | 만료 처리와 늦은 승인이 동시에 → 둘 중 하나만 성공하고, 승인이 지면 자동 취소 |
| `InstallStatusForwardOnlyTest` | ACTIVE 이후 INSTALLED 콜백 → 상태 유지, STALE_IGNORED |
| `RefundEligibilityTest` | DB는 QR_VIEWED, 공급사는 INSTALLED → 환불 거절 + 상태 갱신 |
| `IccidValidatorTest` | 자릿수, Luhn 체크 디지트, 접두사 89, 중복 등록 거절 |
| `OrderStatusTransitionTest` | 허용표에 없는 전이(예: EXPIRED→PAID) 거부 |
| `HmacVerifierTest` | 본문 한 글자만 달라도 실패, 고정 시간 비교 |

## 4. 테스트 환경 구성

- 통합 테스트는 공통 부모 `support/IntegrationTestSupport`를 상속한다. `PostgreSQLContainer("postgres:16-alpine")` 하나를 모든 테스트가 같이 쓰고(`@ServiceConnection`), Flyway가 스키마를 만든다
- PG 주소는 닿지 않는 곳(`http://localhost:1`)으로 둔다. 테스트가 로컬에서 떠 있는 서버(8080)의 모의 PG를 실수로 부르지 않게 하기 위해서다. 그래서 결제를 요청하면 "결과 모름"으로 READY가 되고, T1은 그 상태에서 확정 로직을 직접 부른다
- 대사 스케줄러 주기는 1시간으로 늘려 테스트 중에 끼어들지 않게 한다
- 테스트끼리는 사용자·멱등키·pgTid를 다르게 써서 데이터가 섞이지 않게 한다(공유 DB를 비우지 않는다)
- 시간을 앞으로 돌려야 하는 테스트(만료 계산 등)가 생기면 그때 고정 `Clock` 빈을 테스트 설정에 넣는다

## 5. 실행과 결과 남기기

```bash
cd backend && ./gradlew test --tests "*Concurrency*" --info | tee concurrency-result.txt
```
결과 요약을 README 질문 3에 붙인다(`05` §8 형식).

## 6. 하지 않는 것과 이유

- 프론트 컴포넌트 단위 테스트: UI는 평가 항목이 아니고 시간 대비 효과가 낮다. 대신 `npm run build`로 서버/클라이언트 경계 오류를 잡는다
- 부하 테스트: 범위 밖이다. 10만 SIM 분석은 계산으로 대신한다(`07` §5)
- 커버리지 수치: 평가하지 않는다

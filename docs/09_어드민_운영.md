# 09. 어드민과 운영 조치

> 2.3-5: 주문 목록 필터와 페이지네이션, 주문 상세의 **한 줄 타임라인**, **이상 건 모아 보기**, 운영자 조치(**수동 환불·발급 재시도**). 조치는 이력에 운영자와 사유가 남고 **두 운영자가 동시에 눌러도 한 번만** 실행되어야 한다. PG 취소 실패 시 재시도하되 **무한 재시도는 금지**한다.

> **지금 구현된 범위 (기본 흐름, 2026-10-21)**
> - 주문 목록 `GET /api/admin/orders`(§1 필터 전부, 페이지네이션, `fetchedAt`), 주문 상세 `GET /api/admin/orders/{orderNo}`(§2 타임라인)
> - 타임라인은 지금 `status_history`만 모은다(주문·그 주문의 결제·프로필 이력). `callback_log`는 주문 ID 컬럼이 없어서 바로 이을 수 없다. `refund_attempt`·`admin_action`은 아직 테이블이 없다
> - 화면: `/admin`(필터·페이지·새로고침·"N초 전 데이터"), `/admin/orders/{orderNo}`(정보 + 타임라인). 동작은 [08 §7](08_프론트_경계.md)
> - **보완 단계**: 타임라인에 콜백 기록 붙이기, §3 이상 건, §4·§5 운영자 조치

## 1. 주문 목록

`GET /api/admin/orders?payStatus=&orderStatus=&installStatus=&simType=&from=&to=&page=0&size=20`

| 필터 | 컬럼 |
|---|---|
| 결제 상태 | `payment.status` (주문의 최신 결제 기준) |
| 발급 상태 | `sim_order.status` |
| 설치 상태 | `sim_profile.install_status` |
| SIM 종류 | `sim_order.sim_type` |
| 기간 | `sim_order.created_at` (화면은 KST 날짜로 입력 → 서버에서 UTC 범위로 변환) |

- 조건이 있을 때만 WHERE에 붙는 **동적 쿼리**는 `AdminOrderQueryRepository`에서 SQL 문자열에 `AND ...`를 이어 붙여 만든다. 값은 항상 `:이름` 파라미터로 넘겨서 SQL에 직접 넣지 않는다(SQL 인젝션 방지). 처음엔 JPA `Specification`으로 하려 했지만, 세 테이블(주문·최신 결제·프로필)을 묶는 읽기라 SQL이 더 잘 보여서 바꿨다(ADR-16)
- 결제는 한 주문에 여러 건일 수 있어서(실패 후 재결제) `LEFT JOIN LATERAL`로 **그 주문의 가장 최근 결제 1건**만 붙인다
- 기간은 KST 날짜로 받아 `[시작일 00:00 KST, 종료일 다음 날 00:00 KST)` UTC 범위로 바꾼다. 예: KST 5/9 하루 = UTC 5/8 15:00 ~ 5/9 15:00
- 페이지네이션은 `LIMIT/OFFSET`(offset 방식)이고 `size`는 최대 100이다. 데이터가 아주 많아지면 offset이 느려지므로 커서 방식이 필요해진다(한계)
- 응답에는 `fetchedAt`이 포함된다(`08` §5)

## 2. 주문 상세: 한 줄 타임라인

여러 테이블에 흩어진 기록을 **시간순 한 줄**로 합친다.

| 출처 테이블 | 타임라인에 보이는 형태 (예) |
|---|---|
| `status_history` | `10:00:03 주문 PENDING→PAID · PG · 웹훅` |
| `callback_log` | `10:00:04 PG 웹훅 수신 · 중복 무시` / `10:00:09 공급사 콜백 · 서명 실패` |
| `refund_attempt` | `10:06:12 환불 시도 2/3 실패 · PG 503` |
| `admin_action` | `10:20:00 수동 환불 요청 · ADMIN:kim · 사유 "고객 요청, 미설치 확인"` |

정렬은 **기록 시각**(`status_history.created_at`, 같으면 id) 순서다. 우리가 그 일을 안 순서대로 보여 주고, 늦게 온 신호는 아래 두 시각으로 구분한다.

각 줄에는 **언제**(KST 표시, 늦은 신호면 `발생 09:55 / 기록 10:05`처럼 두 시각을 모두 표시), **무엇이**, **누가/어떤 신호로**를 담는다. 과제가 요구한 세 요소 그대로다.

## 3. 이상 건 모아 보기 — 기준

`GET /api/admin/anomalies`. 각 이상 건에는 **분류, 발생 후 경과 시간, 권장 조치**를 함께 보여 준다.

| 분류 | 기준 (내가 정한 값) | 왜 이 기준인가 | 권장 조치 |
|---|---|---|---|
| `PAID_NOT_ISSUED` | `PAID`/`ISSUING`이고 `paid_at`이 **10분** 넘게 지남 | 정상 발급은 수 초, 재시도를 다 해도 약 6분이므로 10분이면 비정상 | 발급 재시도 또는 수동 환불 |
| `ISSUE_FAILED` | `ISSUE_FAILED` 상태 | 자동 환불로 곧 넘어가야 함. 남아 있으면 이상 | 환불 진행 확인 |
| `REFUND_STUCK` | `REFUNDING`이 **30분** 넘게 지남 | 재시도 3회는 약 6분(즉시+1분+5분)이면 끝남. PG 응답 지연까지 감안해 넉넉히 30분 | 상태 확인 |
| `REFUND_FAILED` | `REFUND_FAILED` 상태 | 자동 처리 포기 = 사람이 해야 함 | §4 절차 |
| `PAYMENT_UNKNOWN` | `payment.READY`가 **15분** 넘게 지남 | 대사 스케줄러도 확정하지 못함 | PG 관리자 화면에서 확인 |
| `AMOUNT_MISMATCH` | 금액이 다른 웹훅 | 위변조나 PG 오류 | PG 문의 |
| `UNMATCHED_CALLBACK` | 주문을 찾을 수 없는 콜백 | `05` §6 | 원문 확인 |
| `SIGNATURE_INVALID` | 서명 실패 콜백이 **1시간에 5건** 이상 | 키 설정 오류나 공격 | 키 확인 |
| `LATE_AFTER_FAIL` | 실패·환불 후 도착한 발급 콜백 | 프로필이 살아 있을 수 있음 | 공급사에 회수 요청 |
| `SIGNAL_CONFLICT` | 설치 신호가 서로 모순됨 | `07` §3 | 공급사 확인 |
| `POLL_FAILING` | 상태 조회 연속 5회 실패 | | 공급사 확인 |
| (가산점) `NOT_INSTALLED_AFTER_START` | 여행 시작일이 지났는데 미설치 | 사용자 안내가 필요함 | 안내 메시지 발송 |

기준 숫자는 모두 `application.yml`의 `anomaly.*` 설정값으로 둔다. 숫자 자체는 근거 데이터 없이 정한 초기값이라 README에 그렇게 적는다.

## 4. 환불 재시도와 "3번 실패한 돈" (인터뷰 I7)

### 재시도 정책
```
1차 시도: 즉시  → 실패 → 2차: 1분 뒤 → 실패 → 3차: 5분 뒤 → 실패 → REFUND_FAILED
(refund_attempt.next_retry_at = 실패 시각 + [1분, 5분][attempt_count-1] / max_attempts = 3)
```
- **재시도할 실패**: 타임아웃, 5xx. 일시적일 수 있다
- **재시도하지 않을 실패**: 4xx(예: 취소 가능 금액 초과). 다시 해도 같은 결과이므로 바로 `REFUND_FAILED`로 보내고 사유를 남긴다
- **"이미 취소됨" 응답**: 이전 시도가 사실은 성공했는데 응답만 못 받은 경우다. 성공으로 처리한다(멱등키 덕분에 판단할 수 있음)
- 매 시도 전에 PG 상태를 먼저 조회한다. 이전 시도가 성공했으면 다시 취소하지 않는다

> **백오프(backoff)**: 실패할 때마다 다음 시도까지의 간격을 늘리는 것. 장애가 난 상대 서버를 연속 요청으로 더 괴롭히지 않기 위함이다.

> **왜 무한 재시도가 금지인가**: 영원히 실패하는 요청(잘못된 금액 등)을 계속 보내면 PG에 부하를 주고, 무엇보다 **아무도 모르는 채로 돈이 묶여 있게** 된다. 상한이 있어야 "사람이 봐야 하는 상태"로 넘어갈 수 있다.

### 환불을 3번 재시도해도 실패했다. 이 돈은 어떻게 되나?
1. **돈은 아직 고객 카드에 청구된 상태다**(우리 쪽에 있음). 시스템은 이것을 숨기지 않는다
2. 주문은 `REFUND_FAILED`가 되고 **이상 건 최상단**에 경과 시간과 함께 계속 보인다. 자동으로 사라지지 않는다
3. 운영자 절차
   - (1) PG 관리자 화면에서 실제 취소 여부를 확인한다. 응답만 실패하고 실제로는 취소됐을 수 있다
   - (2) 취소되지 않았으면 원인(PG 장애 / 취소 불가 사유)을 확인하고 어드민에서 **[환불 재시도]**를 누른다(`REFUND_FAILED → REFUNDING`, 시도 횟수는 새로 시작)
   - (3) PG로 끝내 취소할 수 없으면 계좌 이체 같은 **수동 환불**을 하고, 어드민에서 "외부 처리 완료"로 사유와 함께 마감한다(가능하면 구현, 아니면 한계로 명시)
4. 사용자 화면에는 "환불 처리가 지연되고 있습니다. 담당자가 확인 중입니다"를 보여 준다

**1년차 말투**: "3번 실패하면 시스템은 더 이상 혼자 해결하려 하지 않고 운영자에게 넘깁니다. 중요한 건 이 돈이 어디에 있는지를 시스템이 알고 있고, 이상 건 화면에서 사라지지 않는다는 점입니다. 응답만 실패했을 수도 있어서 운영자는 PG 화면부터 확인하게 했습니다."

## 5. 운영자 조치와 동시성

| 조치 | 가능한 주문 상태 | 동작 |
|---|---|---|
| 수동 환불(전액) | `PAID`, `ISSUED`(미설치), `PICKUP_READY`, `ISSUE_FAILED`, `REFUND_FAILED` | `→ REFUNDING` 선점 → 환불 흐름 |
| 부분 환불 | 결제 `APPROVED` | `refund_attempt(amount < 결제금액)` → 결제 `PARTIAL_CANCELED` |
| 발급 재시도 | `ISSUE_FAILED`, 오래 머문 `ISSUING` | `issue_attempts` 초기화 후 `→ ISSUING` 선점 → 발급 요청 |

공통 규칙
- 요청 본문에 `reason`(필수)과 `requestKey`(화면이 클릭마다 생성한 UUID)를 담는다. 헤더 `X-Admin-Id`도 필요하다
- 처리 순서
  1. `admin_action` INSERT. `request_key UNIQUE`가 같은 클릭의 중복을 막는다
  2. 주문 상태 조건부 UPDATE. 다른 운영자의 동시 조치는 여기서 0행이 된다
  3. 0행이면 `admin_action.result = REJECTED_ALREADY_PROCESSED`로 저장하고 "이미 처리 중(처리자, 시각)"을 응답한다
- 동시성 증명은 `AdminRefundConcurrencyTest`가 맡는다(`11`)
- 수동 환불도 **설치 여부를 확인**한다. 다만 운영자가 예외 환불을 할 수 있도록 `force=true`(사유 필수, 이력에 "설치 확인 무시"로 기록)를 허용한다

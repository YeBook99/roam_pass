# 01. 아키텍처 개요

## 1. 전체 구조 한눈에 보기

### 핵심 포인트
- **모의 PG와 공급사는 같은 Spring 앱 안에 있지만, 우리 코드는 이들을 진짜 외부 서버처럼 HTTP로만 호출한다.** 자바 메서드를 직접 부르면 타임아웃, 중복 콜백, 순서 뒤바뀜 같은 "네트워크 너머의 문제"를 재현할 수 없기 때문이다
- 모의 시스템의 데이터는 `mock` 스키마에 따로 둔다. 원래는 남의 서버이므로 우리 테이블과 섞지 않는다
- 서버가 하나라서 무료 배포가 쉽다. 대신 "실제로는 공급사 장애가 우리 서버 장애와 무관해야 한다"는 점은 재현되지 않는다(한계)

## 2. 백엔드 패키지 구조

기준은 레이어드 설계 문서(`.claude/skills/layered-architecture/ARCHITECTURE.md`, ADR-15)다. **기능으로 먼저 나누고, 그 안을 계층으로 나눈다.** 기능 하나에 `controller / service / repository / domain / dto / exception`이 들어간다.

```
com.roampass
├─ plan          요금제 조회                                       ✅
├─ order         주문 생성·조회, 결제 확정(PENDING→PAID), 만료 스케줄러(예정)   ✅
├─ payment       결제 요청, PG 웹훅, 대사 스케줄러, 환불(예정)              ✅
├─ issue         eSIM 발급 요청·콜백, 설치 추적·만료 계산 ✅ / 발급 재시도, USIM ICCID 등록 (예정)
├─ admin         어드민 주문 목록·상세 타임라인 ✅ / 이상 건·조치 (예정)
├─ history       상태 이력(status_history) 기록. 여러 기능이 함께 쓰는 업무라 주인 기능으로 분리  ✅
├─ callback      웹훅·콜백 수신 기록(callback_log), HMAC 서명                ✅
├─ mockpg        모의 PG (승인/취소/조회/웹훅 발송, 설정)                    ✅
├─ mocksupplier  모의 공급사 (발급/콜백/프로필 조회, 시연용 상태 변경)           ✅
├─ infra
│   └─ pg        PG 호출(PgClient 인터페이스 + HttpPgClient), 타임아웃, 외부 형식 ↔ 우리 결과 변환  ✅
└─ global        업무 규칙이 없는 기술 공통 코드만
    ├─ config    Clock·KST, JPA Auditing, 스케줄링
    ├─ error     ErrorCode, BusinessException, GlobalExceptionHandler(ProblemDetail)
    └─ entity    BaseTimeEntity(created_at·updated_at)
```

- 의존은 Controller → Service → Repository로만 흐르고, 다른 기능의 데이터는 그 기능의 Service로만 다룬다(예: 결제 → `OrderService.markPaid`). 이 규칙은 `ArchitectureTest`(ArchUnit)가 빌드마다 검사한다
- 처음에는 도메인별 패키지 안에 클래스를 평평하게 두는 3계층(ADR-08)이었다. 결제까지 만든 뒤 기능마다 모양이 달라지고 패키지 순환이 생겨서 ADR-15로 다시 정리했다

## 3. 대표 흐름: 이심 구매 (정상 경로)

```mermaid
sequenceDiagram
    autonumber
    participant B as 브라우저
    participant API as 우리 API
    participant DB as DB
    participant PG as 모의 PG
    participant S as 모의 공급사

    B->>API: POST /api/orders (planId, travelStartDate)
    API->>DB: sim_order 저장 (PENDING, expires_at=+10분)
    B->>API: POST /api/orders/{no}/payments (Idempotency-Key)
    API->>DB: payment 저장 (READY)  [tx1]
    API->>PG: POST /mock/pg/approve (트랜잭션 밖)
    PG-->>API: approved, pgTid
    API->>DB: 결제 확정: 주문 PENDING→PAID  [tx2]
    Note over API: 커밋 후 OrderPaidEvent → @Async 발급 시작
    PG-->>API: 웹훅 approved (중복 가능) → 이미 처리됨, 무시
    API-->>B: 200 (주문 상태 PAID)
    B->>B: 발급 대기 화면으로 이동, 2초 폴링

    API->>DB: 주문 PAID→ISSUING, 시도횟수+1  [tx3]
    API->>S: POST /mock/supplier/orders (orderNo를 멱등키로)
    S-->>API: 202 supplierOrderNo
    API->>DB: supplier_order_no 저장  [tx4]
    S-->>API: (몇 초 뒤) 발급 콜백 + X-Signature
    API->>DB: 서명 검증 → sim_profile 저장, 주문 ISSUING→ISSUED
    B->>API: 폴링 GET /api/my/orders/{no}
    API-->>B: ISSUED + QR/활성화 코드
```

**브라우저를 3번 직후에 닫아도** 8번 이후는 모두 서버가 혼자 진행한다. 8번의 이벤트가 유실되면(서버 재시작 등) 스케줄러가 `PAID` 상태로 남은 주문을 다시 집어 간다(`04_상태설계.md` §5).

## 4. 실패 경로 요약

| 상황 | 누가 처리 | 결과 |
|---|---|---|
| PG 승인 응답 타임아웃 | 웹훅 또는 대사 스케줄러 | PG 상태 조회로 확정 |
| 결제 10분 미완료 | 만료 스케줄러 | EXPIRED (늦은 승인은 자동 취소) |
| 공급사 접수 실패/콜백 없음 | 발급 재시도 스케줄러 | 최대 3회 → ISSUE_FAILED → 자동 환불 |
| 자동 환불(PG 취소) 실패 | 환불 재시도 스케줄러 | 최대 3회 → REFUND_FAILED → 어드민 이상 건 |
| 서명 틀린 콜백 | 콜백 컨트롤러 | 401 + callback_log 기록 |
| 설치 콜백 누락 | 설치 폴링 스케줄러 | 공급사 상태 조회로 보정 |

## 5. 시연 방법 (README "시연 방법"의 원본)

**화면으로 하기 (2026-10-22~)**: 왼쪽 메뉴 **시연 → 시연 설정**(`/demo`)에서 상황 버튼을 누르면 아래 표의 설정이 한 번에 바뀌고, 무슨 일이 생기는지와 어디서 확인하는지가 같이 보인다. 세부 값은 같은 화면의 폼에서 직접 바꾸고, [정상으로 되돌리기]로 처음 값으로 돌린다. 설치·개통 흉내는 시연 화면에서 주문번호를 넣거나, 운영 주문 상세 화면 아래 "공급사 SIM 상태 바꾸기"에서 버튼으로 한다. 화면은 아래 주소를 그대로 부른다.

모의 PG와 공급사의 동작은 **설정값**으로 바꾼다. `PUT /mock/pg/config`, `PUT /mock/supplier/config`에 바꿀 값만 보내고, `POST /mock/reset`으로 기본값에 되돌린다. 요청마다 쿼리 파라미터로 바꾸는 방식은 만들지 않았다. 과제는 "쿼리 파라미터나 설정값"이라고 했고, 설정값 하나로 모든 경우를 재현할 수 있어서다.

| 시연하고 싶은 것 | 방법 (`PUT /mock/pg/config` 본문) |
|---|---|
| 결제 실패 | `{"failApprove": true}` |
| 웹훅 지연 | `{"webhookDelayMs": 5000}` |
| 웹훅 중복 | `{"webhookCount": 3}` |
| 웹훅 누락 | `{"webhookCount": 0}` |
| 승인됐는데 응답 타임아웃 | `{"responseDelayMs": 4000}` (우리 쪽 타임아웃 3초) → READY → 1분 뒤 대사로 확정 |
| 웹훅 금액 조작 | `{"webhookAmountDelta": -1000}` |
| 발급 실패 | (보완 단계) supplier config `issueFailRate=1.0` |
| 발급 콜백 지연 | 지금은 `application.yml`의 `mock.supplier.callback-delay-ms`(기본 3000). 중복·누락·순서 뒤바뀜과 `PUT /mock/supplier/config`는 보완 단계 |
| 서명 위조 콜백 | `POST /mock/supplier/debug/forged-callback` |
| PG 취소 실패 | pg config `{"cancelFailRate": 1.0}` (5xx) |
| 설치·개통 흉내 | `POST /mock/supplier/profiles/{iccid}/state` `{ "state": "INSTALLED" }` 또는 `{ "state": "ENABLED", "activatedAt": "2026-05-01T15:20:00Z" }`(activatedAt을 비우면 지금). 1분 안에 스케줄러가 반영하거나, 사용자가 `POST /api/my/orders/{orderNo}/profile/refresh`로 바로 확인 |
| 콜백 누락된 설치 | 지금은 설치 콜백 자체가 없고 조회로만 반영한다. `DELETED`, `sendCallback` 옵션은 보완 단계 |

> 시연용 엔드포인트는 `mock.enabled=true`일 때만 켜진다. 실제 서비스라면 존재하면 안 되는 API이므로 운영 프로필에서는 끈다는 전제다.

## 6. 인증 (평가 대상 아님)

- 사용자: `X-User-Id` 헤더. 첫 화면에서 아이디를 입력하면 쿠키에 저장하고, 모든 요청에 헤더로 붙인다
- 운영자: `X-Admin-Id` 헤더. `/admin` 화면에서 운영자 아이디를 입력한다
- 모든 `/api/my/**` 조회는 `user_id = X-User-Id` 조건을 건다. 다른 사람 주문을 볼 수 없게 하는 최소한의 방어다

## 7. 한계 (인터뷰에서 먼저 말할 것)

- 앱이 하나라서 모의 공급사 장애와 우리 서버 장애가 분리되지 않는다
- 스케줄러는 **서버 1대**를 가정한다. 2대 이상이면 같은 작업을 동시에 집을 수 있다. 다만 조건부 UPDATE로 상태를 선점하므로 결과가 중복되지는 않고, 불필요한 HTTP 호출이 중복될 뿐이다. 근본 해결은 ShedLock이다
- 인증이 헤더라서 누구나 남의 아이디로 조회할 수 있다(과제 명시사항이라 범위 밖)

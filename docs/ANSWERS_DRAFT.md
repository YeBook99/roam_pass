## 2.4 반드시 답해야 하는 8개 질문

### Q1. 왜 이 기술들을 골랐습니까? (필수)

큰 틀(Next.js / Spring / 관계형 DB)은 과제에서 정해져 있었고, 나머지는 **"짧은 시간 안에 정합성 설계에 집중할 수 있는가"** 를 기준으로 골랐습니다.

- **DB — MySQL 8**: 익숙해서 골랐습니다. 이번 과제에서 필요한 건 유니크 제약, 트랜잭션, 그리고 작업 큐용 `SELECT … FOR UPDATE SKIP LOCKED`였는데 MySQL 8에 전부 있습니다. 회사가 PostgreSQL을 쓴다는 건 알았지만, 처음 쓰는 DB의 특성까지 공부하면 정작 중복 처리 설계에 쓸 시간이 줄어든다고 판단했습니다. 대신 MySQL의 `DATETIME`에는 시간대가 없다는 점 때문에 "DB에는 무조건 UTC로 저장"을 규칙으로 정했습니다.
- **Next.js — App Router + 서버 컴포넌트 조회 + 클라이언트 폴링**: 요금제 목록, 내 SIM, 어드민 목록처럼 "읽기만 하는 화면"은 서버 컴포넌트에서 바로 백엔드를 불러 그리고, 결제 버튼·발급 대기·운영자 조치 버튼처럼 상호작용이 있는 부분만 클라이언트 컴포넌트로 뺐습니다. 이렇게 하면 "어디까지가 서버고 어디부터가 브라우저인지"가 파일 단위로 보입니다. Pages Router도 고려했지만 신규 프로젝트 기본값이 App Router라 이쪽을 택했습니다.
- **Spring — JPA + 상태 변경만 조건부 UPDATE**: 일반적인 저장·조회는 JPA로 빠르게 만들고, 중복이 문제가 되는 상태 변경(결제 승인, 발급 완료, 환불 시작)만 `UPDATE … WHERE status = '이전 상태'`로 직접 썼습니다. JPA로 엔티티를 읽고 바꾸면 두 요청이 동시에 "아직 READY네?"라고 읽고 둘 다 바꿀 수 있기 때문입니다. MyBatis도 고려했지만 매핑 코드가 늘어나서 버렸습니다.
- **비동기 작업 — DB 작업 테이블 + `@Scheduled` 폴러**: "결제 완료"를 저장하는 같은 트랜잭션 안에 "발급해야 함"이라는 작업 행을 같이 넣고, 스케줄러가 그 행을 주워서 처리합니다. 서버가 죽거나 무료 호스팅이 잠들어도 작업이 DB에 남아 있어서 깨어나면 이어서 처리합니다. Kafka나 Redis 큐도 생각했지만, 무료로 띄우기 어렵고 "DB 저장은 됐는데 메시지 발행은 실패"라는 문제가 새로 생겨서 버렸습니다. `@Async`는 메모리에만 있어서 재시작하면 사라지므로 버렸습니다.
- **Flyway**: SQL 파일 그대로라 DDL을 그대로 보여 줄 수 있고, 앱이 뜰 때 자동으로 적용돼서 "빈 DB에서 재현"이 쉽습니다.
- **Testcontainers**: 동시성 테스트는 진짜 MySQL의 유니크 제약과 락 동작을 봐야 의미가 있어서 H2 대신 골랐습니다.
- **배포 — Vercel + Render + 【교체: 실제 쓴 MySQL 호스팅】**: 전부 무료 티어입니다. 【교체: 고른 이유, 막힌 지점】
- **직접 추가한 라이브러리**: 【교체: 실제 추가한 것만. 예) springdoc-openapi — API 명세 자동 생성 / qrcode — 활성화 코드 QR 렌더링】
- 【본인】 위 내용 중 내 실제 이유와 다른 부분은 내 말로 고친다. "익숙해서"가 진짜 이유면 그렇게 쓴다.

### Q2. 결제부터 발급까지 주문 상태를 어떻게 설계했습니까?

주문 상태 하나에 모든 걸 넣지 않고 **주문 / 결제 / 설치 / 환불을 서로 다른 상태로** 나눴습니다. 어드민이 "결제 상태"와 "발급·설치 상태"를 따로 걸러 봐야 하고, 한 컬럼에 다 넣으면 "결제는 취소됐는데 SIM은 설치됨" 같은 상황을 표현할 수 없어서입니다.

주문 상태: `PENDING → PAID → ISSUING → ISSUED` (유심은 `PAID → PICKUP_READY → ACTIVATING → ISSUED`), 실패 쪽은 `ISSUE_FAILED → REFUNDING → REFUNDED / REFUND_FAILED`, 미결제는 `PENDING → EXPIRED`. (상태도는 README 다이어그램 【교체: mermaid 그림 위치】)

- **결제는 됐는데 발급이 안 된 주문은 어디 있나**: `PAID` 또는 `ISSUING`에 있습니다. 그리고 이 상태로 바뀌는 트랜잭션 안에서 반드시 "발급 작업" 행을 같이 만들기 때문에, **이 상태의 주문에는 항상 처리 중인 작업이 하나 붙어 있습니다.**
- **누가 끝내나**:
  1. 정상이면 공급사 콜백이 `ISSUED`로 끝냅니다.
  2. 콜백이 안 오면 스케줄러의 "발급 확인" 작업이 공급사에 직접 물어봐서 끝냅니다.
  3. 정해진 시간(【교체: 10분】)이 지나도 안 되면 스케줄러가 `ISSUE_FAILED`로 바꾸고 자동 환불을 시작합니다.
  4. 환불도 최대 횟수만큼 실패하면 `REFUND_FAILED`가 되어 어드민 "이상 건"에 뜨고, 운영자가 사유를 남기고 끝냅니다.
- **사용자가 결제 직후 브라우저를 닫으면**: 아무 영향이 없습니다. 발급을 브라우저가 이어서 부르는 구조가 아니라 처음부터 서버 작업이 진행하기 때문입니다. 결제 승인 응답을 받기 전에 닫혔다면 PG 웹훅이 결제를 반영하고, 웹훅도 빠지면 결제 대사 작업이 PG 조회 API로 확정합니다. 사용자는 나중에 "내 SIM"에서 결과를 봅니다.

### Q3. 중복 처리를 어떻게 막았고, 어떻게 증명했습니까?

두 겹으로 막았습니다.

1. **유니크 제약 (DB가 "두 개 생기는 것"을 막음)**
   - `payment.idempotency_key` — 결제 버튼 연타·재시도
   - `callback_log.event_key` — 같은 웹훅/콜백 N번 (`PG:{tid}:APPROVED`, `SUPPLIER:{supplierOrderNo}:ISSUED`처럼 **본문 해시가 아니라 상대가 준 ID + 이벤트 종류**로 만들었습니다. 본문 해시는 재전송 시각 같은 필드만 달라져도 다른 이벤트로 착각하기 때문입니다)
   - `sim_profile.order_id / iccid / supplier_order_no` — 한 주문에 프로필 2개
2. **조건부 UPDATE (상태를 "두 번 바꾸는 것"을 막음)**
   - `UPDATE payment SET status='APPROVED' WHERE id=? AND status='READY'` → 영향받은 행이 1이면 내가 처음, 0이면 이미 누가 처리함. 승인 응답과 웹훅이 동시에 와도 한쪽만 후속 처리를 합니다.

**버린 방법**: 비관적 락(`SELECT … FOR UPDATE`)으로 전부 처리하는 건 락 범위를 실수하기 쉽고, 락을 잡은 채로 외부 API를 부르는 실수를 하게 만들어서 작업 선점에만 썼습니다. `@Version` 낙관적 락만 쓰면 충돌 시 예외가 나서 재시도 코드가 필요합니다. Redis 분산 락은 서버 1대에 인프라만 늘어납니다.

**증명**: `ExecutorService`로 스레드 20개를 만들고 `CountDownLatch`로 동시에 출발시켜 같은 웹훅/콜백을 보내는 테스트를 만들었습니다.
- `PaymentWebhookConcurrencyTest` — 결제 APPROVED 1건, 발급 작업 1개, 상태 이력 1줄
- `SupplierCallbackConcurrencyTest` — 프로필 1개, 나머지 19개는 DUPLICATE 기록

### Q4. 트랜잭션 경계는 어디에 그었습니까?

**PG 호출과 공급사 호출은 전부 트랜잭션 밖입니다.**
`[TX1] 결제 시도 저장 → 커밋 → (밖) PG 호출 → [TX2] 결과 반영 + 다음 작업 생성 → 커밋`

트랜잭션 안에서 외부 API를 부르면 두 가지가 문제입니다. PG가 5초 걸리면 그동안 DB 커넥션과 락을 붙잡고 있고, PG는 승인했는데 우리 트랜잭션이 롤백되면 "돈은 나갔는데 기록이 없는" 상태가 됩니다. 그래서 외부 호출 전후로 작은 트랜잭션을 나눴고, TX2가 실패해도 웹훅이나 대사 작업이 **같은 반영 메서드**로 다시 반영하게 했습니다.

- **공급사가 접수는 했는데 우리 DB 저장이 실패하면**: 발급 요청에 우리 주문번호를 멱등 키로 넣어 보냅니다. 재시도 때 같은 주문번호로 다시 요청하면 공급사가 새로 발급하지 않고 기존 접수번호를 돌려줍니다. 콜백에도 우리 주문번호가 들어 있어서, 접수번호를 저장하지 못했어도 주문을 찾을 수 있습니다.
- **결제 버튼 연타**: 결제 화면에서 만든 `Idempotency-Key`(UUID)를 매번 같이 보냅니다. 같은 키면 PG를 다시 부르지 않고 저장된 결과를 돌려줍니다.
- **타임아웃 후 재시도**: 사용자가 다시 눌러도 같은 키라 새 결제가 생기지 않습니다. 결과를 모르는 결제(`READY`로 남은 것)는 결제 대사 작업이 PG 조회 API로 확정합니다. 키가 달라도 주문당 승인 결제는 1개만 되도록 주문 쪽 조건부 UPDATE가 한 번 더 막습니다.

### Q5. "이 사용자가 SIM을 설치했다"를 무엇으로 판단합니까?

**공급사 상태를 정답으로 봅니다.** 우리가 직접 아는 신호는 "사용자가 우리 화면에서 QR을 열었다"뿐인데, 이건 설치하려고 했다는 정황이지 설치했다는 증거는 아닙니다.

- **신호별 신뢰도**: QR 열람(우리 기록, 확실하지만 설치 아님) < 개통 콜백(확실하지만 가끔 빠짐) ≈ 상태 조회(확실하지만 조회한 시점 기준).
- **콜백이 빠지거나 늦을 때**: 콜백은 "빨리 알게 해 주는 길", 상태 조회 폴링은 "빠진 걸 메우는 길"로 두고, 둘 다 같은 메서드를 탑니다. 그리고 설치 상태는 **앞으로만** 갑니다 (`WHERE install_rank < 새 rank`). 그래서 ACTIVE가 된 뒤에 늦게 도착한 INSTALLED 신호는 상태를 되돌리지 못하고 이력에만 남습니다.
- **얼마나 자주, 어떤 주문만**: 모든 SIM을 매분 보지 않습니다. 곧 설치할 가능성이 높은 것만 자주 봅니다. QR을 연 SIM은 5분, 설치됐지만 아직 개통 전인 SIM은 15분, 사용 중은 1시간, 여행 시작이 멀리 남은 SIM은 6시간, 만료·환불된 SIM은 안 봅니다. 그리고 **환불 요청이 들어온 순간에는 반드시 1번 실시간 조회**합니다.
- **신호가 틀렸을 때 보이는 것**: 사용자 화면에는 "공급사 기준 상태: 설치됨 (3분 전 확인)"처럼 출처와 확인 시각이 같이 나옵니다. 어드민 타임라인에는 어떤 신호(QR / 콜백 / 조회 / 운영자)로 언제 바뀌었는지가 줄마다 남습니다. 환불 요청 때 공급사 조회가 실패하면 환불하지 않고 "확인 중"으로 두고 이상 건에 올립니다. **모르면 돈을 내보내지 않는다**가 원칙입니다.

### Q6. 어드민과 사용자 화면에서 서버와 클라이언트의 경계를 어디에 그었습니까?

- **조회는 서버, 상호작용은 클라이언트**: 요금제 목록, 내 SIM, 어드민 목록·상세는 서버 컴포넌트에서 백엔드를 불러 HTML을 만들어 보냅니다. 결제 버튼(멱등 키, 버튼 잠금), 발급 대기(폴링), QR 보기 버튼, 운영자 조치 버튼만 클라이언트 컴포넌트입니다.
- **백엔드 호출 경로**: 브라우저는 Spring을 직접 부르지 않고 Next.js의 `/api/*` 라우트 핸들러를 거칩니다. 여기서 쿠키에 있는 사용자/운영자 ID를 `X-User-Id` / `X-Admin-Id` 헤더로 붙입니다. CORS 설정이 필요 없고 백엔드 주소도 브라우저에 안 보입니다.
- **발급 대기 화면은 결과를 어떻게 받나**: **폴링**입니다. 2초 → 5초 → 10초로 간격을 늘리고, 발급 완료·실패면 멈추고, 탭이 안 보이면 멈춥니다. SSE도 생각했는데, 몇 초 늦어도 괜찮은 화면이고 무료 호스팅이 잠들거나 프록시가 연결을 끊는 환경에서 연결을 유지하는 게 더 불안정하다고 판단했습니다. 기다리는 동안 "창을 닫아도 발급은 계속됩니다"와 "내 SIM으로 가기"를 보여 줍니다.
- **운영자가 보는 결제 상태가 몇 초 전 데이터인지**: 어드민 화면은 캐시 없이(`no-store`) 매번 조회하고, 상단에 "조회 시각 14:03:21 KST (n초 전)"을 표시합니다. 그리고 SIM마다 "공급사와 마지막으로 맞춘 시각"을 따로 보여 줘서 "DB 기준 최신"과 "공급사 기준 최신"의 차이를 드러냈습니다.

### Q8. 시간이 더 있었다면 무엇을 했겠습니까?

【교체: 실제로 못 한 것 기준으로 다시 정렬】 초안 우선순위:
1. **공급사 추상화** — 실무에서 공급사가 두 곳 이상이고 상태 이름이 다르다는 점이 가장 자주 부딪히는 문제라고 해서, 공급사별 어댑터로 상태를 우리 상태로 바꾸는 인터페이스를 만들고 싶습니다.
2. **관측성** — 지금은 이상 건을 사람이 화면에서 봐야 합니다. 환불 실패·작업 DEAD를 슬랙 같은 곳으로 알림 보내는 게 운영에서 가장 먼저 필요할 것 같습니다.
3. **폴링 확장** — 활성 SIM이 많아지면 지금 구조(스케줄러 1개가 DB에서 순서대로 조회)가 먼저 한계에 닿습니다. 배치 조회 API, 워커 여러 대, 공급사 rate limit 대응.
4. **데이터 사용량 알림(50%/100%, 한 번만)**, 장기 미설치 안내.
5. 무료 호스팅 슬립 문제의 근본 해결(유료 상시 인스턴스 or 외부 스케줄러).

## 2.9 2차 인터뷰 예상 질문

> 답의 모범 형태: **"이렇게 했다 → 이런 경우엔 이렇게 된다 → 이 부분은 이런 한계가 있다"**

**Q. 왜 이 기술을 골랐습니까? 다른 선택지와 비교해 본 적이 있습니까?**
→ Q1 요약. 비교한 것: MySQL vs PostgreSQL, JPA만 vs 조건부 UPDATE, 큐(Kafka/Redis) vs DB 작업 테이블, 폴링 vs SSE. 각각 버린 이유 한 줄씩.

**Q. 처음 써본 것이 막혔을 때 어떻게 뚫었습니까? AI가 준 코드 중 버린 것이 있습니까?**
→ 【본인】 LEARNING_LOG에서 가장 구체적인 사례 1개. "AI가 ~라고 했는데 실행해 보니 ~라서 공식 문서의 ~를 보고 고쳤다" 형태.

**Q. PG 승인은 성공했는데 응답을 못 받고 타임아웃이 났습니다. 이 결제의 상태를 어떻게 확정합니까?**
→ 우리 쪽 결제는 `READY`(결과 모름)로 남습니다. 확정하는 길은 세 가지이고 모두 같은 반영 메서드를 탑니다. ① PG 웹훅이 오면 그걸로 확정 ② 사용자가 재시도하면 같은 멱등 키라 PG가 기존 결과를 돌려줌 ③ 둘 다 없으면 결제 대사 작업이 PG 조회 API로 확정. 그 사이 주문이 10분 만료에 걸려도 `READY` 결제가 있으면 바로 만료시키지 않고 PG부터 확인하고, 만약 만료 후에 승인이 확인되면 자동 취소합니다. 한계: 대사 주기(【교체】)만큼은 사용자가 "결제 확인 중"을 보게 됩니다.

**Q. 공급사가 발급 콜백을 영영 보내지 않으면 이 주문은 어떻게 끝납니까?**
→ 발급 접수와 동시에 "발급 확인" 작업이 예약됩니다. 이 작업이 공급사 조회 API로 직접 확인해서 발급됐으면 콜백과 같은 메서드로 프로필을 저장하고, 【교체: 10분】이 지나도 안 되면 `ISSUE_FAILED`로 바꾸고 자동 환불을 시작합니다. 콜백은 빨리 알기 위한 수단이고 정답은 조회로 확정한다는 구조입니다. 한계: 환불한 뒤에 공급사가 늦게 발급해 버리면 → 그 콜백은 프로필로 붙이지 않고 "환불 후 발급" 이상 건으로 올려 공급사 취소를 사람이 처리하게 했습니다.

**Q. 공급사 콜백의 서명은 맞는데 우리 DB에 없는 주문번호가 왔습니다. 어떻게 합니까?**
→ 서명이 맞다는 건 공급사가 보낸 게 맞다는 뜻이지 우리 주문이라는 뜻은 아닙니다. 먼저 콜백 안의 우리 주문번호로 한 번 더 찾고(접수번호 저장이 실패했을 수 있으니까), 그래도 없으면 `callback_log`에 `UNMATCHED`로 원문을 저장하고 200을 돌려준 뒤 어드민 이상 건에 띄웁니다. 200을 주는 이유는 재전송을 받아도 없는 주문이 생기지 않기 때문입니다. 대신 원문을 남겨서 나중에 대조할 수 있게 했습니다. (반대로 일시적인 DB 오류라면 5xx를 줘서 재전송을 받는 게 맞다고 생각합니다.)

**Q. 사용자가 "설치 안 했으니 환불해 달라"는데 공급사 상태는 INSTALLED입니다. 누구 말이 맞습니까?**
→ 시스템 판단은 공급사 쪽입니다. 기기에 프로필이 내려받아졌는지는 공급사만 알 수 있고, 사용자는 "설치"의 의미를 다르게 이해했을 수도 있습니다(예: 다운로드는 됐는데 개통이 안 됨). 그래서 시스템은 환불 불가로 응답하고, 운영자는 타임라인(언제 어떤 신호로 INSTALLED가 됐는지)을 근거로 응대합니다. 다만 공급사 오류일 수도 있으니 운영자가 사유를 남기고 수동 환불할 수 있는 길은 열어 뒀습니다.

**Q. 환불을 3번 재시도해도 실패했습니다. 이 돈은 어떻게 됩니까?**
→ 아직 고객에게 돌아가지 않은 상태이고, 시스템은 그걸 숨기지 않고 `REFUND_FAILED` + 이상 건 + 이력으로 사람에게 넘깁니다. 운영자는 실패 원인(마지막 에러)을 보고 다시 시도하거나, PG 관리 화면에서 직접 취소한 뒤 사유를 남기고 종결합니다. 무한 재시도를 안 하는 이유는 PG 장애 때 요청 폭탄이 되기 때문이고, 재시도 전에는 PG 조회로 "사실은 이미 취소됐는지"를 확인해서 이중 취소를 막습니다.

**Q. 활성 SIM이 10만 개가 되면 상태 조회 폴링에서 가장 먼저 터지는 곳은 어디입니까?**
→ 제 구조에서는 **공급사 API 호출 수**가 먼저 터질 것 같습니다. 10만 개를 평균 30분마다 보면 초당 약 55건인데, 스케줄러 하나가 순서대로 HTTP를 부르면 처리량이 못 따라가고 공급사 rate limit에도 걸립니다. 그다음은 `next_poll_at` 조회 쿼리와 인덱스입니다. 대응: 상태별 주기를 더 차등화, 공급사가 배치 조회를 주면 묶어서 조회, 워커를 여러 대로 늘리기(SKIP LOCKED라 가능), 콜백 신뢰도가 높으면 폴링 주기 더 늘리기. 【교체: 직접 측정했다면 숫자】

**Q. 배포한 곳에서 트래픽이 10배가 되면 무엇부터 손봐야 합니까?**
→ 무료 인스턴스 1대라 **슬립과 단일 인스턴스**부터 바꿔야 합니다. 상시 켜진 인스턴스로 바꾸고, DB 커넥션 풀 크기와 무료 DB 연결 수 제한을 확인합니다. 그다음 발급 대기 화면의 폴링 요청이 사용자 수에 비례해 늘어나니 폴링 간격 조정이나 캐시를 봅니다. 스케줄러는 SKIP LOCKED라 인스턴스를 늘려도 같은 작업을 두 번 잡지 않습니다. 【본인: 실제로 배포해 보며 느낀 병목이 있으면 그걸 1순위로】

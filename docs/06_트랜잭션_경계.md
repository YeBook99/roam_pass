# 06. 트랜잭션 경계 (질문 4)

> 질문 4: PG 호출과 공급사 호출은 DB 트랜잭션 **안**입니까 **밖**입니까? 공급사가 **접수는 했는데 우리 DB 저장이 실패**하면 어떻게 됩니까? **결제 버튼 연타 · 타임아웃 후 재시도**는 각각 **어떤 키로** 막습니까?

먼저 읽을 것: [L2 Spring 비동기·스케줄러](learn/L2_Spring_비동기_스케줄러.md) §2(`@Transactional`이 하는 일)

## 1. 결론: 외부 호출은 항상 트랜잭션 **밖**

```
[tx1: 상태 선점 + 요청 기록 → 커밋]  →  HTTP 호출 (트랜잭션 없음)  →  [tx2: 결과 저장 → 커밋]
```

### 왜 밖에 두나 — 안에 두면 생기는 문제 세 가지
1. **DB 커넥션과 락을 오래 잡는다.** PG가 3초 걸리면 그 3초 동안 커넥션 하나와 주문 행 락이 묶인다. 커넥션 풀(기본 10개)이 금방 바닥나서 전혀 상관없는 요청까지 멈춘다
2. **롤백해도 외부 세계는 되돌릴 수 없다.** PG가 승인한 뒤 우리 쪽 저장에서 예외가 나서 롤백되면, DB에는 결제 기록이 없는데 돈은 빠져나간 상태가 된다. 트랜잭션 안에 있다고 안전한 게 아니라 **오히려 흔적이 사라진다**
3. **무엇을 보냈는지 기록이 없다.** tx1에서 "보내기 직전" 상태(`payment.READY`, `order.ISSUING`)를 먼저 커밋해 두어야, HTTP 결과를 모르는 상황에서도 "보냈을 수 있다"는 흔적이 남는다. 이 흔적이 있어야 나중에 조회로 확정할 수 있다

**1년차 말투**: "처음엔 서비스 메서드 전체에 `@Transactional`을 붙였는데, 그러면 PG를 기다리는 동안 DB 커넥션을 잡고 있게 된다는 걸 알았습니다. 그리고 더 중요한 건, 승인은 났는데 저장에서 롤백되면 결제 흔적이 아예 사라진다는 점이었습니다. 그래서 '보내기 전에 먼저 기록하고 커밋, 그다음 호출, 결과는 새 트랜잭션에 저장' 순서로 나눴습니다."

## 2. 결제 흐름의 트랜잭션 분할

```java
// PaymentFacade (트랜잭션 없음 — 순서를 조율하는 역할)
public PaymentResponse pay(String orderNo, String userId, String idempotencyKey) {
    // tx1: 결제 행 생성 (멱등키 UNIQUE). 이미 있으면 기존 결과 반환
    Payment p = paymentTxService.createOrGet(orderNo, userId, idempotencyKey);   // @Transactional
    if (p.isFinal()) return PaymentResponse.of(p);           // 재시도면 이미 결과가 있음
    if (p.isInFlightByOtherRequest()) return PaymentResponse.processing(p);

    // 외부 호출: 트랜잭션 밖, 타임아웃 3초
    PgResult r;
    try {
        r = pgClient.approve(p.getOrderNo(), p.getAmount(), p.getId());  // PG에도 우리 paymentId를 멱등키로 전달
    } catch (PgTimeoutException e) {
        return PaymentResponse.processing(p);                // READY 유지 → 웹훅 또는 대사가 확정
    }

    // tx2: 결과 반영 (웹훅과 같은 경로)
    paymentConfirmService.confirm(r, Signal.API);           // @Transactional
    return PaymentResponse.of(paymentRepository.findById(p.getId()));
}
```

> ⚠️ **Spring 함정**: `@Transactional`은 **다른 빈(bean)을 통해 호출할 때만** 적용된다. 같은 클래스 안에서 `this.createOrGet()`을 부르면 트랜잭션이 걸리지 않는다. 그래서 트랜잭션이 필요한 부분을 `PaymentTxService`, `PaymentConfirmService`라는 **별도 클래스**로 뺐다 ([L2 §2.3](learn/L2_Spring_비동기_스케줄러.md#23-자주-하는-실수-같은-클래스-안에서-호출하면-적용-안-됨)).

## 3. 발급 흐름의 트랜잭션 분할

```
tx1: 주문 PAID→ISSUING (조건부), issue_attempts+1, issue_requested_at=now  → 커밋
     ↳ 0행이면 종료 (다른 스레드가 이미 요청 중)
HTTP: POST /mock/supplier/orders { orderNo, planCode, callbackUrl }   ← orderNo가 공급사 쪽 멱등키
tx2: sim_order.supplier_order_no = 응답값 → 커밋
```

HTTP가 실패하면(타임아웃, 5xx) 주문은 `ISSUING` 상태로 두고 `last_error`만 기록한다. 발급 스케줄러가 2분 뒤 다시 시도한다.

## 4. PG 승인은 성공했는데 응답을 못 받고 타임아웃이 났다면? (인터뷰 I3)

이 상황을 위해 결제 상태 `READY`가 있다.

1. tx1에서 `payment.READY`가 이미 커밋되어 있다. 우리는 "보냈다"는 사실은 알고 결과만 모른다
2. 사용자에게는 "결제 확인 중"을 보여 준다(실패라고 하지 않는다. 실제로는 돈이 빠져나갔을 수 있으니까)
3. 결과를 확정하는 경로는 세 가지다. 먼저 오는 쪽이 확정하고 나머지는 중복으로 무시된다(§05-3)
   - **PG 웹훅**: 보통 몇 초 안에 온다
   - **대사(reconciliation) 스케줄러**: 1분마다 `READY`로 1분 넘게 남은 결제를 찾아 `GET /mock/pg/payments?orderNo=`로 **PG에 직접 물어본다**. 승인이면 confirm, 기록이 없으면 FAILED 처리
   - **사용자 재시도**: 같은 Idempotency-Key로 다시 요청하면 기존 READY 행이 반환되고, 이때 PG 조회를 한 번 수행한다
4. 그래도 15분 넘게 `READY`이면(PG 조회 API도 장애) 어드민 이상 건 "결제 결과 미확정"으로 올린다

> **대사(reconciliation)**: 원래 회계 용어로 "두 장부를 맞춰 보는 것"이다. 여기서는 우리 DB의 결제 상태와 PG의 기록을 비교해서 맞추는 작업을 말한다.

**핵심 원칙: 타임아웃은 "실패"가 아니라 "모름"이다.** 모를 때는 확인될 때까지 기다리고 확인하는 수단을 둔다.

## 5. 공급사가 접수는 했는데 우리 DB 저장(tx2)이 실패하면?

상황: 공급사는 `202 { supplierOrderNo: "S-123" }`을 줬는데 tx2에서 DB 오류나 서버 다운으로 supplierOrderNo 저장에 실패했다.

1. 주문은 `ISSUING`이고 `supplier_order_no`는 비어 있다. tx1이 커밋됐으므로 "보냈다"는 흔적은 있다
2. **콜백이 먼저 도착하는 경우**: 콜백 본문의 `orderNo`(우리가 요청할 때 넘긴 값)로 주문을 찾을 수 있다. 그 자리에서 supplierOrderNo를 채우고 정상 처리한다(§05-6)
3. **콜백도 안 오는 경우**: 2분 뒤 스케줄러가 재요청한다. 이때 **같은 orderNo**를 보내므로, 공급사는 "이미 접수된 주문"으로 보고 **같은 supplierOrderNo를 다시 돌려준다**(모의 공급사가 orderNo 기준 멱등으로 구현됨). 프로필이 두 개 생기지 않는다
4. 실제 공급사가 멱등을 지원하지 않는다면, 재요청 전에 "orderNo로 공급사 주문 조회"를 먼저 하도록 바꿔야 한다(한계)

**한 줄 요약**: "공급사에 우리 주문번호를 멱등키로 넘겼기 때문에, 저장에 실패해도 다시 요청하면 같은 결과를 돌려받습니다."

## 6. 연타와 재시도는 각각 어떤 키로 막나

| 상황 | 키 | 누가 만드나 | 어디서 막나 |
|---|---|---|---|
| **결제 버튼 연타** | `Idempotency-Key` | 화면이 **결제 페이지에 들어올 때 한 번** UUID를 만든다(클릭할 때마다 새로 만들지 않음) | `payment.idempotency_key UNIQUE`. 두 번째 요청은 INSERT 충돌 → 기존 행 반환 |
| **타임아웃 후 재시도** | 같은 `Idempotency-Key` | 화면의 재시도는 **같은 키를 재사용** | 같은 행이 반환됨. READY이면 PG 조회 후 결과 반환 |
| 다른 탭에서 동시에 결제 | (키가 다름) | - | `payment (order_id) WHERE status='READY'` 부분 유니크 → 하나만 진행 |
| 우리 서버 → PG 재요청 | `paymentId` | 서버 | 모의 PG가 merchant 요청 ID로 멱등 처리 |
| 우리 서버 → 공급사 재요청 | `orderNo` | 서버 | 모의 공급사가 orderNo로 멱등 처리 |
| 환불(PG 취소) 재시도 | `refund_attempt.request_key` | 서버 | 모의 PG가 취소 요청 ID로 멱등 처리 |
| 결제 실패 후 다시 결제 | **새** `Idempotency-Key` | 화면이 실패를 보여 준 뒤 새로 생성 | 실패한 결제는 최종 상태이므로 새 시도가 가능 |

**연타와 재시도를 같은 키로 막는 이유**: 서버 입장에서 둘은 구분할 수 없다. 둘 다 "같은 의도의 요청이 또 왔다"이므로 같은 키로 같은 결과를 돌려주는 것이 맞다.

## 7. 결제 만료와 늦게 온 승인이 겹치면

- 만료 스케줄러: `UPDATE sim_order SET status='EXPIRED' WHERE status='PENDING' AND expires_at < now() AND id NOT IN (2분 이내에 READY 결제가 있는 주문)`
  - 결제가 진행 중인 주문은 2분 더 기다려 준다(유예)
- 그래도 `EXPIRED` 이후에 승인이 도착하면(웹훅 지연 등) 주문 `PENDING→PAID` 조건부 UPDATE가 0행이 된다. 이를 감지해서 **자동 취소(환불)**를 시작하고 이력에 "만료 후 승인 → 자동 취소"를 남긴다
- 즉 만료와 결제 중 **딱 하나만** 이긴다. 진 쪽은 반드시 정리된다

## 8. 콜백·웹훅 처리의 트랜잭션

콜백 처리는 **하나의 트랜잭션** 안에서 끝난다. 범위는 중복 기록, 상태 변경, 이력 저장이다. 외부 호출이 없으므로 짧다. 커밋이 끝난 뒤에 응답(200)을 준다. 커밋 전에 200을 주면, 응답 후 커밋이 실패했을 때 공급사는 성공한 줄 알고 재전송하지 않는다.

## 9. 이벤트와 커밋의 관계

`OrderPaidEvent`는 `@TransactionalEventListener(phase = AFTER_COMMIT)`으로 받는다. **결제 확정이 커밋된 뒤에만** 발급이 시작되므로 "롤백된 결제에 대해 발급이 나가는" 일이 없다. 반대로 커밋 직후 서버가 죽으면 이벤트가 유실될 수 있다. 이것은 발급 스케줄러가 `PAID` 방치 주문을 주워 가는 방식으로 메운다(`04` §5).

> **트랜잭셔널 아웃박스(outbox) 패턴**과의 비교: 정석은 "보낼 메시지를 같은 트랜잭션에서 outbox 테이블에 저장하고 별도 프로세스가 전송"하는 방식이다. 나는 **주문 상태(`PAID`) 자체가 outbox 역할**을 한다고 봤다. 스케줄러가 `PAID` 상태를 보고 할 일을 알 수 있기 때문이다. 이벤트 종류가 많아지면 별도 outbox 테이블이 필요해진다.

## 10. 한계

- PG와 공급사가 우리 멱등키를 지원한다고 가정했다(모의 시스템이라 직접 그렇게 만들었다). 실제 연동 시에는 각 업체 명세를 확인해야 한다
- 대사 스케줄러 주기(1분)만큼 사용자가 "결제 확인 중"을 볼 수 있다
- 만료 유예 2분은 임의로 정한 값이다

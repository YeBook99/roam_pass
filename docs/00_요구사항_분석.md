# 00. 요구사항 분석

> 이 문서의 목적: 과제 PDF(14쪽)를 **체크리스트**로 쪼개고, 각 항목이 어느 설계 문서에서 답해지는지 연결한다.
> 마지막 표(커버리지 매트릭스)에 빈칸이 있으면 아직 답하지 못한 질문이 있다는 뜻이다.

## 1. 과제를 한 문장으로

여행자용 데이터 SIM 판매 서비스 **ROAMPASS**의 한 줄기를 끝에서 끝까지 만든다. 그 줄기는 다음 순서로 이어진다.

```
요금제 선택·주문(PENDING) → 결제(모의 PG) → 발급(모의 공급사, 콜백) → 어드민 확인 → 설치·개통 추적
```

상품은 두 종류다.
- **이심(eSIM)**: QR 코드로 휴대폰에 프로필을 내려받는다. 공급사가 발급하고, 결과는 **나중에 콜백으로** 온다
- **유심(USIM)**: 공항에서 실물 카드를 받는다. 사용자가 카드 뒷면의 ICCID를 입력하면 그때 개통을 요청한다

## 2. 과제가 진짜로 보려는 것

PDF 1쪽과 11쪽을 읽고 정리한 결론은 다음과 같다.

1. **이해하고 만들었는가.** 2차 인터뷰에서 내 코드를 설명할 수 있어야 한다
2. **짧은 시간에 어디까지 습득하는가.** 처음 써 본 기술과 그것을 익힌 과정을 높게 평가한다
3. **완성도보다 판단 근거를 본다.** "여기까지 했고 이건 몰라서 못 했다"고 설명할 수 있으면 괜찮다
4. **"문제없다"고 우기는 것이 가장 나쁘다.** 한계를 알고 있다는 것을 보여 줘야 한다

그래서 나는 이 과제를 "기능을 많이 만드는 과제"가 아니라 **"돈이 걸린 흐름이 꼬이지 않게 만들고 그 이유를 설명하는 과제"**로 이해했다.

## 3. 평가 비중 → 시간 배분

| 영역 | 비중 | 내가 쓸 시간 비율 | 이유 |
|---|---|---|---|
| 이해도·설명 | 30% | 30% | 문서(이 docs 폴더)와 인터뷰 준비 |
| 결제·발급 정합성 | 25% | 30% | 중복·보상 로직이 가장 어렵고 버그가 나기 쉬움 |
| 기술 선택 근거 | 15% | 5% | 결정할 때마다 ADR에 바로 기록하면 따로 시간이 거의 들지 않음 |
| 요구사항 충족 | 15% | 20% | 어드민 이상 건, 설치 추적 |
| 테스트 | 10% | 10% | 동시성 2개 + 보상 1개 + 만료 1개 |
| 배포·재현성 | 5% | 5% | AWS 프리티어, README 커맨드 |

## 4. 필수 요구사항 체크리스트 (2.3)

### 4.1 요금제 조회·주문 생성
- [ ] 국가/일수/데이터 용량별 요금제 목록이 있고, 각 요금제는 ESIM 또는 USIM이다
- [ ] 요금제와 **여행 시작일**로 주문을 만들고 상태는 `PENDING`이다
- [ ] 결제 대기에 **만료 시간**을 둔다(10분)
→ `03_데이터모델.md`, `04_상태설계.md`

### 4.2 결제 (모의 PG 직접 구현)
- [ ] 승인 API: 금액과 주문번호를 받아 `approved` 또는 `failed`를 반환한다
- [ ] 승인 결과를 **웹훅으로 한 번 더** 통지한다
- [ ] 지연·실패·중복 통지를 **쿼리 파라미터나 설정으로** 조절할 수 있다
- [ ] 취소 API: 전액과 부분 취소를 지원한다
- [ ] 승인 응답과 통지가 둘 다 오거나 통지가 N번 와도 **결제는 한 번만** 처리한다
- [ ] 통지 금액이 주문 금액과 다르면 결제 완료로 처리하지 않는다
→ `05_정합성_멱등성.md`, `06_트랜잭션_경계.md`

### 4.3 발급(이심)·수령 대기(유심)
- [ ] 이심: 결제 후 공급사에 발급을 요청한다. 공급사는 접수만 즉시 응답하고, ICCID와 활성화 코드는 **몇 초 뒤 콜백**으로 보낸다
- [ ] 콜백 **서명을 검증**하고, 중복이나 순서 뒤바뀜이 와도 **프로필이 두 번 붙지 않는다**
- [ ] 결제됐는데 발급이 최종 실패하면 **자동 환불하거나 운영자가 인지할 흔적**을 남긴다
- [ ] 결제 직후 **브라우저를 닫아도** 발급이 끝까지 진행된다
- [ ] 유심: `PICKUP_READY`로 두고, ICCID 입력 시 개통을 요청한다. 형식이나 체크 디지트가 틀린 ICCID와 이미 등록된 ICCID는 거절한다
→ `04_상태설계.md`, `05`, `06`

### 4.4 설치·사용 추적
- [ ] SIM마다 설치 상태를 둔다(ISSUED / QR_VIEWED / INSTALLED / ACTIVE / EXPIRED)
- [ ] 상태 조회 API와 개통 콜백(가끔 누락됨)을 **어떻게 조합할지** 정한다
- [ ] 만료 계산에서 UTC와 KST 차이가 틀리지 않는다
- [ ] 설치·개통된 SIM은 환불 불가로 하고, **늦은 신호**를 고려한다
→ `07_설치추적_만료.md`

### 4.5 어드민
- [ ] 주문 목록 필터: 결제 상태, 발급·설치 상태, SIM 종류, 기간. 페이지네이션 포함
- [ ] 주문 상세: 결제·발급·설치 이력을 **한 줄 타임라인**으로 보여 준다(언제, 무엇이, 누가/어떤 신호로)
- [ ] 이상 건 모아 보기: 기준은 직접 정한다
- [ ] 운영자 조치: 수동 환불과 발급 재시도. **운영자와 사유를 기록**하고, **두 명이 동시에 눌러도 한 번만** 실행한다
- [ ] PG 취소 실패 시 재시도 경로를 두되 **무한 재시도는 금지**. 최대 횟수를 넘으면 운영자 확인 대상으로 분류한다
→ `09_어드민_운영.md`

### 4.6 사용자 화면
- [ ] 구매: 요금제 → 결제 → 발급 대기. 발급이 늦어도 사용자가 할 수 있는 일이 있어야 한다
- [ ] 내 SIM: 목록과 상세(결제 금액, 발급·설치 상태, QR과 활성화 코드, 남은 기간, 환불 가능 여부), 유심 ICCID 등록
→ `08_프론트_경계.md`, [L1 Next.js 기초](learn/L1_Nextjs_기초.md)

### 4.7 범위 밖 (시간 쓰지 말 것)
- 회원 시스템: `X-User-Id`와 `X-Admin-Id` 헤더면 충분하다
- 실제 기기 설치: 모의 공급사의 상태를 바꾸는 엔드포인트로 흉내 낸다
- UI 완성도: 기본 HTML이어도 감점이 없다

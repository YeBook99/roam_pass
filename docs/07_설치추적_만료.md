# 07. 설치·사용 추적과 만료 계산 (질문 5)

> 질문 5: "이 사용자가 SIM을 설치했다"를 **무엇으로 판단**합니까? 어떤 신호를 **얼마나 믿었는지**, 콜백이 빠지거나 늦을 때 **어떻게 메웠는지**, 상태 조회는 **얼마나 자주, 어떤 주문만** 하는지 적어 주세요. 신호가 틀렸을 때 사용자·운영자는 **무엇을 보게** 됩니까?

> **지금 구현된 범위 (기본 흐름, 2026-10-21)**
> - QR 열람 기록(`POST /api/my/orders/{orderNo}/profile/qr-view`), 공급사 상태 조회(`GET /profiles/{iccid}`)로 INSTALLED·ACTIVE 반영, 상태는 앞으로만(`InstallStatus.canMoveTo`)
> - 개통 시 만료일 = `activated_at + days × 24h`(`ExpiryCalculator`, 테스트 `ExpiryCalculatorTest`), 만료 시각이 지나면 EXPIRED
> - `InstallPollingScheduler`: 개통 전 SIM을 **모두 1분마다** 조회(아래 §5의 SIM별 주기는 아직 아님), 사용자 [다시 확인](`.../profile/refresh`)
> - 공급사가 설치 확인 없이 바로 ENABLED면 ISSUED·QR_VIEWED에서 ACTIVE로 건너뛴다(앞으로만 가므로 허용). 이때 `installed_at`은 확인한 시각으로 채운다
> - **보완 단계**: 공급사 설치 콜백 수신, §5 선택적 폴링(지금은 끝내 설치하지 않은 SIM도 기간 제한 없이 매분 조회), 조회 연속 실패를 이상 건으로 노출, DELETED·SIGNAL_CONFLICT, 환불 직전 동기 조회(§6), 발생 시각(`occurred_at`)에 공급사 시각 넣기

## 1. 용어부터: "신호"란?

우리는 사용자의 휴대폰을 직접 볼 수 없다. 그래서 **다른 곳에서 오는 정보**로 설치 여부를 추측한다. 이 정보 하나하나를 **신호**라고 부른다.

| 신호 | 누가 만드나 | 빠르기 | 확실성 | 한계 |
|---|---|---|---|---|
| **QR 열람** | 우리 서비스 (사용자가 QR 화면을 열 때 기록) | 즉시 | 우리가 직접 기록하므로 **기록 자체는 확실함** | "봤다"일 뿐 **설치했다는 증거가 아님** |
| **공급사 콜백** | 공급사가 상태가 바뀔 때 보내 줌 | 빠름(수 초) | 서명이 맞으면 내용은 진짜 | **가끔 빠지거나 늦게 옴** (과제 명시) |
| **공급사 상태 조회** | 우리가 `GET /profiles/{iccid}`로 물어봄 | 물어볼 때만 알 수 있음 | **물어본 그 순간의 공급사 기록** = 가장 확실 | 자주 물으면 비용·부하가 큼 |

### "신뢰도 순서"의 의미
세 신호가 서로 다른 말을 할 때 **어느 쪽을 기준으로 삼을지** 정한 순서다.

```
설치 판단의 근거로 쓰는 힘:   상태 조회  >  콜백  >  QR 열람(근거로 쓰지 않음)
반영되는 속도:              콜백  >  상태 조회
```

- **콜백 = 빠른 힌트.** 오면 바로 반영한다. 사용자 화면이 빨리 바뀐다
- **상태 조회 = 사실 확인.** 콜백이 빠져도 주기적인 조회가 결국 맞춰 준다. **환불처럼 돈이 걸린 판단 직전에는 반드시 조회한다**
- **QR 열람 = 참고 정보.** "곧 설치할 사람"이라는 힌트로만 쓴다. 이 사람은 더 자주 조회한다(§5)

**1년차 말투**: "설치는 사용자 폰에서 일어나서 우리가 직접 볼 수 없습니다. 우리가 직접 아는 건 'QR을 열어 봤다'뿐이라 그건 근거로 안 썼습니다. 공급사 콜백은 빠르지만 빠질 수 있어서 '오면 반영'만 하고, 빠진 건 주기적인 상태 조회로 메웠습니다. 그리고 환불 버튼을 누른 순간에는 무조건 공급사에 한 번 더 물어보고 판단합니다."

## 2. 설치 상태와 공급사 상태 매핑

| 우리 `install_status` | 순위 | 뜻 | 들어오는 신호 |
|---|---|---|---|
| `ISSUED` | 1 | 발급 완료. QR·활성화 코드를 보여 줄 수 있음 | 발급 콜백 |
| `QR_VIEWED` | 2 | 사용자가 우리 화면에서 QR을 열람함 | 우리 API |
| `INSTALLED` | 3 | 기기에 프로필이 내려받아짐 | 공급사 `INSTALLED` (콜백/조회) |
| `ACTIVE` | 4 | 현지에서 개통되어 사용 시작. `activated_at` 기록 | 공급사 `ENABLED` (콜백/조회) |
| `EXPIRED` | 5 | 사용 기간 종료 | 우리가 계산 (`expires_at < now`) |
| `DELETED` | 특수 | 사용자가 기기에서 프로필을 지움 | 공급사 `DELETED` |

공급사 상태 `RELEASED`는 "발급됐지만 아직 내려받지 않음"이다. 우리 상태는 `ISSUED`나 `QR_VIEWED`에 해당하며 아무것도 바꾸지 않는다.

## 3. 상태는 되돌아갈 수 있나? DELETED는? (부록 A-2)

**원칙: 앞으로만 간다(순위가 올라가는 방향만 허용).**

이유는 두 가지다.
1. **신호는 늦게 도착한다.** "INSTALLED" 콜백이 "ENABLED" 조회 결과보다 늦게 오면, 그대로 반영할 경우 ACTIVE가 INSTALLED로 되돌아간다. 순위를 비교하면 늦게 온 옛날 신호를 자연스럽게 무시할 수 있다(`STALE_IGNORED`로 기록)
2. **환불 판단이 안전한 쪽으로 기운다.** 한 번이라도 설치가 확인됐다면 환불 불가 상태를 유지한다. 돈이 나가는 쪽의 실수(설치한 사람에게 환불)를 막는 편이 낫다고 봤다

**DELETED 처리**
- `INSTALLED`나 `ACTIVE`에서 `DELETED`로 가면 그대로 기록한다. **환불은 여전히 불가**다. 한 번 설치된 이심 프로필은 보통 다시 내려받을 수 없어서 재발급 문의 대상이다. 사용자 화면에는 "기기에서 삭제됨. 재설치가 필요하면 고객센터 문의"를 보여 준다
- `ISSUED`나 `QR_VIEWED`에서 `DELETED`로 가면(설치한 적이 없는데 삭제) 이상한 상황이다. 어드민 이상 건(`SIGNAL_CONFLICT`)으로 올린다

**신호끼리 모순될 때**: 콜백은 INSTALLED였는데 이후 조회는 RELEASED라고 하면, 상태를 되돌리지 않고 `SIGNAL_CONFLICT`로 기록해 운영자가 보게 한다. 되돌리지 않는 이유는 위 2번과 같다(환불 쪽 보수적 판단).

## 4. 만료일 계산 — UTC와 KST (부록 A-3)

### 규칙
```
expires_at (UTC Instant) = activated_at (공급사가 준 UTC Instant) + days × 24시간
화면 표시 = expires_at을 Asia/Seoul로 변환해서 보여 줌
```

### 과제 예시 직접 계산
- `activatedAt = 2026-05-01T15:20:00Z` (UTC)
- 이것을 KST(UTC+9)로 바꾸면 **2026-05-02 00:20 KST**다. 한국 기준으로는 이미 **다음 날**이다
- 7일 요금제: + 168시간 → `2026-05-08T15:20:00Z` → **2026-05-09 00:20 KST에 만료**

### "7일"은 24시간 × 7인가, 날짜 7개인가?
| 방식 | 이 예시의 만료 | 장점 | 단점 |
|---|---|---|---|
| **24시간 × 7 (채택)** | 05-09 00:20 KST | 누구에게나 정확히 168시간. **타임존과 무관**하게 같은 결과 | "며칠까지"라고 말하기 애매함 |
| 날짜 7개 (KST 달력 기준) | 05-02 ~ 05-08 23:59 KST | 설명이 쉬움 | 밤 11시에 개통하면 첫날을 1시간만 씀. **해외에 있는 사용자에게 KST 달력은 의미가 없음** |

**고른 이유**: 사용자는 해외에 있다. 그 나라 시간으로도, 한국 시간으로도 똑같이 "168시간"인 방식이 가장 공정하고 오해가 적다고 판단했다. 실제 서비스라면 공급사 계약 기준을 따라야 하는 부분이라 README에 **가정**으로 적는다.

### 흔한 실수 (테스트로 막을 것)
- `LocalDateTime`으로 받아서 타임존 정보를 잃어버리는 실수. `2026-05-01T15:20`을 KST로 착각하면 **9시간 일찍** 만료된다
- 서버 기본 타임존(`TimeZone.getDefault()`)에 의존하는 실수. EC2는 UTC, 내 노트북은 KST라서 **로컬에서는 맞고 배포하면 틀리는** 버그가 생긴다 → `Clock`을 주입하고 `ZoneId.of("Asia/Seoul")`를 명시한다
- 화면에서 `new Date().toLocaleString()`을 그대로 쓰는 실수. 브라우저 타임존에 따라 다르게 보인다 → `timeZone: 'Asia/Seoul'`을 명시한다

```java
// 개념 코드
public static Instant expiresAt(Instant activatedAt, int days) {
    return activatedAt.plus(Duration.ofHours(24L * days));
}
public static ZonedDateTime toKst(Instant t) {
    return t.atZone(ZoneId.of("Asia/Seoul"));
}
```

### 만료 처리
- `expires_at`은 개통(ACTIVE) 시점에 한 번 계산해서 저장한다
- `EXPIRED` 상태 전환은 1시간 주기 스케줄러가 한다. **화면의 "남은 기간"은 저장된 `expires_at - now`로 실시간 계산**하므로 스케줄러가 늦어도 사용자는 정확한 남은 시간을 본다

## 5. 상태 조회(폴링)는 얼마나 자주, 어떤 SIM만? (부록 A-4)

**모든 활성 SIM을 매분 조회할 필요는 없다.** 상태가 **곧 바뀔 가능성이 높은** SIM만 자주 보고, 나머지는 드물게 본다.

| 대상 | 조회 주기 | 이유 |
|---|---|---|
| 발급 직후 (ISSUED) | **1분 뒤 1회** | 순서가 뒤바뀐 설치 이벤트를 바로잡는 첫 확인 |
| QR을 **최근 1시간 안에** 열람함 | **2분** | 지금 설치하고 있을 가능성이 높음 |
| 미설치 + 여행 시작일 **D-1 ~ D+2** | **10분** | 출국 직전이나 도착 직후라 설치·개통이 임박함 |
| 미설치 + 그 외 | **6시간** | 당분간 변할 일이 적음 |
| INSTALLED (개통 대기) + 여행 시작일 이후 | **10분** | 현지 도착 후 곧 개통됨 → `activated_at`이 만료 계산에 필요 |
| INSTALLED + 여행 시작일 전 | **1시간** | |
| ACTIVE | **1시간** | 사용량(가산점) 확인용. 만료는 우리가 계산하므로 조회가 필요 없음 |
| EXPIRED / DELETED / 환불된 주문 | **조회 안 함** | 더 바뀔 것이 없음 |
| **환불 요청 직전** | **즉시 1회(동기)** | 돈이 걸린 판단 |

구현 방식
- `sim_profile.next_poll_at`에 "다음에 볼 시각"을 저장한다. 스케줄러는 1분마다 `next_poll_at <= now`인 SIM을 **최대 100개**만 가져와 조회한다
- 조회할 때마다 위 표에 따라 `next_poll_at`을 다시 계산한다
- 콜백이 오면 그 SIM의 `next_poll_at`을 늦춘다. 방금 사실을 받았으므로 바로 조회할 필요가 없다
- 조회에 실패하면 `poll_fail_count`를 늘리고 간격을 늘린다. 연속 5회 실패하면 어드민 이상 건으로 올린다

### 활성 SIM이 10만 개가 되면 가장 먼저 터지는 곳은? (인터뷰 I8)

계산해 보면 이렇다.
- 10만 개가 대부분 ACTIVE(1시간 주기)라면 **시간당 10만 건 ≈ 분당 1,700건 ≈ 초당 28건**이다
- 지금 구조는 **스케줄러 스레드 1개가 순서대로** HTTP를 호출한다. 1건에 200ms면 초당 5건이 한계다

따라서 다음 순서로 터진다.
1. **스케줄러 처리량**: 한 번에 100건, 1분 주기로는 분당 1,700건을 따라가지 못해 `next_poll_at`이 계속 밀린다. 해결책은 병렬 처리(스레드풀)와 여러 인스턴스 분산(`FOR UPDATE SKIP LOCKED`)이다
2. **공급사 API rate limit**: 공급사가 초당 호출 수를 제한하면 429 에러가 난다. 해결책은 공급사의 **일괄 조회 API**, 또는 콜백 신뢰도를 높이고 조회는 대사 용도로만 축소하는 것이다
3. DB `next_poll_at` 조회: 인덱스가 있으므로 마지막 순서다

**1년차 말투**: "지금은 스케줄러 하나가 하나씩 물어보는 구조라서, 10만 개가 되면 공급사보다 우리 스케줄러가 먼저 밀릴 것 같습니다. 계산해 보면 초당 28건을 처리해야 하는데 지금 구조는 초당 5건 정도라서요."

## 6. 환불 가능 판단과 늦은 신호

**규칙: `INSTALLED`, `ACTIVE`, `EXPIRED`, `DELETED(설치 후)`이면 환불 불가. `ISSUED`, `QR_VIEWED`이면 환불 가능.**

늦은 신호 때문에 틀릴 수 있는 상황과 대응은 다음과 같다.

| 상황 | 대응 |
|---|---|
| 실제로는 설치했는데 콜백이 빠져서 우리 DB는 `QR_VIEWED` | 환불 요청 시 **공급사 상태를 동기 조회**한다. `INSTALLED`면 거절하고 상태를 갱신한다 |
| 조회 API가 장애로 응답하지 않음 | **환불하지 않고 보류**한다. "확인 후 처리"로 운영자에게 넘긴다(돈을 내보내는 쪽으로 추측하지 않음) |
| 조회 시점에는 RELEASED였는데, 환불 처리 중에 사용자가 설치함 | 이상적으로는 PG 취소 전에 **공급사에 프로필 비활성화를 요청**해야 한다. 이번 범위에서는 환불 후 설치가 감지되면 `REFUND_AFTER_INSTALL` 이상 건으로 남긴다(한계) |

### "설치 안 했으니 환불해 달라"는데 공급사 상태는 INSTALLED라면? (인터뷰 I6)
- **기본적으로 공급사 기록을 믿는다.** 공급사(정확히는 이심 프로필을 내려 주는 서버)는 프로필이 **어떤 기기로 내려받아졌는지** 기록하는 당사자이기 때문이다
- 그렇다고 사용자가 거짓말한다고 단정하지는 않는다. 가능한 경우는 이렇다
  - 사용자가 설치한 것을 잊었다
  - **다른 기기에서 QR을 스캔했다**(가족 폰, 캡처해서 공유)
  - 공급사 오류
- 그래서 시스템은 자동 환불을 거절하되, **운영자가 판단할 근거**를 보여 준다
  - 타임라인: QR 열람 시각(우리 기록), 설치 시각(`occurred_at`, 공급사), 신호 출처(콜백/조회), 환불 요청 시각
  - 예: "QR 열람 10:02 → 설치 10:05(공급사) → 환불 요청 14:00" → 설치 후 환불 요청으로 판단할 근거가 된다
- 최종 판단과 예외 환불은 **운영자 수동 환불**(사유 기록 필수)로 처리한다

**1년차 말투**: "시스템은 공급사 기록을 기준으로 자동 환불을 막습니다. 다만 누가 맞는지 판단하는 건 사람의 일이라고 봤고, 운영자가 판단할 수 있게 QR 열람 시각과 설치 시각, 그 정보를 어디서 받았는지를 타임라인에 함께 보여 줍니다."

## 7. 신호가 틀렸을 때 사용자·운영자가 보는 것

| 보는 사람 | 화면 | 내용 |
|---|---|---|
| 사용자 | 내 SIM 상세 | 설치 상태, **"마지막 확인: 12분 전"**, 환불 가능 여부와 그 이유("설치가 확인되어 환불 불가"). 상태가 이상하면 [상태 다시 확인] 버튼 → 즉시 조회 1회(분당 1회로 제한) |
| 운영자 | 주문 상세 타임라인 | 각 상태 변경의 **신호 출처**(CALLBACK/POLLING/API)와 `occurred_at`/`created_at`(기록 시각). 두 시각 차이가 크면 "늦게 도착한 신호" 표시 |
| 운영자 | 이상 건 | `SIGNAL_CONFLICT`(신호 모순), 조회 5회 연속 실패, `REFUND_AFTER_INSTALL`, 여행 시작일이 지났는데 미설치(가산점: 장기 미설치) |

## 8. 한계

- 프로필 비활성화 요청(환불 전 회수)은 구현하지 않았다
- 폴링 주기 숫자(2분, 10분, 6시간)는 근거 데이터 없이 정한 초기값이다. 실제로는 "콜백 누락률"과 "공급사 rate limit"을 보고 조정해야 한다
- 공급사가 둘이 되면 상태 이름이 다를 것이다(가산점: 공급사 추상화). `SupplierClient` 인터페이스가 공급사 상태를 우리 `install_status`로 **변환해서** 돌려주도록 설계해 두었다

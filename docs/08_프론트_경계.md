# 08. 프론트엔드: 서버와 클라이언트의 경계 (질문 6)

> 질문 6: 어드민과 사용자 화면에서 서버와 클라이언트의 경계를 어디에 그었습니까? 발급 대기 화면은 결과를 어떻게 받습니까(폴링 / SSE / 새로고침 등)? 운영자가 보는 결제 상태가 **몇 초 전 데이터인지** 어떻게 드러냈습니까?

**Next.js가 처음이라면 [L1 Next.js 기초](learn/L1_Nextjs_기초.md)를 먼저 읽는다.** 이 문서는 Server Component, Client Component, `'use client'`, 폴링을 안다고 가정한다.

폴더 구조, 의존 방향, fetch·에러·시각 표시 규칙은 [프론트 설계 기준](../.claude/skills/nextjs-architecture/ARCHITECTURE.md)(ADR-17)에 있다. 이 문서는 **화면마다 어디가 서버이고 어디가 브라우저인지**를 정한다.

## 1. 경계를 긋는 나의 기준 (한 문장)

> **"처음 보여 줄 데이터는 서버에서, 사용자가 누르거나 시간이 지나며 바뀌는 것은 브라우저에서."**

| 질문 | 예 → | 아니오 → |
|---|---|---|
| 버튼 클릭, 입력, 타이머(폴링)가 필요한가? | **Client Component** | 다음 질문으로 |
| 페이지에 들어왔을 때 보여 줄 데이터인가? | **Server Component**에서 조회 | 그냥 Server Component(정적 내용) |

## 2. 화면별 설계

| URL | 파일 | 서버 부분 (Server Component) | 클라이언트 부분 (Client Component) |
|---|---|---|---|
| `/` | `app/page.tsx` | 요금제 목록 조회·표시 | `PlanFilter` (국가/일수 필터), `UserIdForm` (아이디 입력 → 쿠키) |

| `/my-sims` | `app/my-sims/page.tsx` | 내 주문 목록 | 없음 (새로고침으로 충분) |

### 이렇게 나눈 이유
- **첫 화면이 비어 있지 않다.** Server Component는 데이터를 채운 HTML을 보내므로 "로딩 중..."이 깜빡이지 않는다
- **브라우저로 보내는 JavaScript가 줄어든다.** 표 같은 정적 부분은 서버에서 끝나고, 버튼이 있는 작은 컴포넌트만 브라우저로 간다
- **필터는 URL에 담는다**(`/admin?payStatus=APPROVED&page=2`). 새로고침하거나 링크를 공유해도 같은 화면이 나오고, 서버 컴포넌트가 URL만 보고 조회하면 된다

## 3. 브라우저와 백엔드의 연결

```
브라우저(Client Component) ──fetch('/api/...')──▶ Next.js 서버 ──rewrites──▶ Spring :8080
Next.js 서버(Server Component) ──fetch(API_INTERNAL_URL + '/api/...')──▶ Spring :8080
```

- **rewrites**(`next.config.ts`)로 `/api/*`를 Spring으로 넘긴다. 브라우저 입장에서는 같은 도메인이므로 **CORS 설정이 필요 없다**
  > **CORS**: 브라우저가 "다른 도메인의 API를 호출할 때" 그 서버의 허락을 확인하는 보안 규칙
- Server Component는 서버 안에서 바로 Spring을 부른다. docker compose에서는 `http://backend:8080`을 쓴다
- 사용자 식별: 첫 화면에서 입력한 아이디를 **쿠키**에 저장한다. Server Component는 `cookies()`로, Client Component는 요청 시 쿠키 값을 읽어 `X-User-Id` 헤더로 붙인다

## 4. 발급 대기 화면은 결과를 어떻게 받나

**결정: 2초 간격 폴링. 최종 상태가 되거나 5분이 지나면 멈춘다.** 실제 코드는 `features/order/components/IssueStatusPoller.tsx`이고 아래는 핵심만 줄인 것이다.

```tsx
'use client';
const FINAL = ['ISSUED', 'PICKUP_READY', 'ISSUE_FAILED', 'REFUNDING', 'REFUNDED', 'REFUND_FAILED', 'EXPIRED'];

export function IssueStatusPoller({ orderNo, initial }: Props) {
  const { data } = useQuery({
    queryKey: ['order', orderNo],
    queryFn: () => fetchOrder(orderNo),
    initialData: initial,                                     // 서버가 준 첫 데이터로 시작
    refetchInterval: (q) => FINAL.includes(q.state.data.status) ? false : 2000,  // 끝나면 중단
  });
  ...
}
```

| 방식 | 판단 |
|---|---|
| **폴링 (채택)** | 단순하다. 서버는 일반 GET API 하나면 된다. 발급은 보통 수 초면 끝나서 요청 수가 적다(약 2~5회) |
| SSE | 서버가 결과를 바로 밀어 주지만, 연결을 유지하는 동안 서버 자원을 쓰고 프록시 타임아웃 설정도 필요하다. 처음 쓰는 기술을 하나 더 늘릴 만큼의 이득이 없다고 봤다 |
| 새로고침 안내 | 사용자에게 일을 떠넘긴다 |

### 발급이 늦어도 사용자가 할 수 있는 일 (2.3-6)
대기 화면에 항상 아래 내용을 보여 준다.
- "발급은 서버에서 계속 진행됩니다. **이 창을 닫아도 괜찮아요.**"
- [내 SIM에서 나중에 확인하기] 링크
- 이심 설치 방법 안내(아이폰/안드로이드). 기다리는 동안 미리 읽어 둘 수 있다
- 30초가 지나도 발급되지 않으면: "평소보다 오래 걸리고 있어요. 조금만 더 기다려 주세요"
- 5분이 지나면 폴링을 멈추고: "자동 확인을 멈췄어요. 잠시 뒤 내 SIM에서 다시 확인해 주세요". 발급 재요청이 아직 없어서 주문이 `ISSUING`에 남을 수 있는데, 창을 열어 둔 동안 끝없이 묻지 않게 하기 위해서다
- `ISSUE_FAILED`면 "발급에 실패했습니다", `REFUNDING`이면 "환불을 진행하고 있습니다"
- 발급 재시도(최대 3회, 약 6분) → 실패 시 자동 환불이 보완 단계에서 구현되면 30초 안내를 "최대 6분 안에 발급되거나, 실패하면 자동으로 환불됩니다"로 바꾼다. **지금은 없는 동작이라 화면에서 약속하지 않는다

## 5. 운영자가 보는 데이터가 몇 초 전 것인지 어떻게 드러내나

1. 백엔드의 모든 어드민 응답에 **`fetchedAt`**(서버가 DB를 조회한 시각)을 넣는다
2. 화면 상단의 `FreshnessBadge`가 `지금 - fetchedAt`을 1초마다 다시 계산해 **"12초 전 데이터"**로 보여 준다. 60초가 넘으면 노란색으로 바뀐다
3. **[새로고침]** 버튼과 **자동 새로고침(10초) 토글**을 둔다
4. 운영자 조치(환불·재시도)를 누르면 **서버가 그 시점의 최신 상태로 다시 판단**한다. 화면이 오래된 데이터를 보여 줬더라도 조건부 UPDATE가 막으므로, "이미 다른 운영자가 처리했습니다" 같은 응답이 올 수 있다. 조치가 끝나면 목록을 즉시 다시 불러온다
5. 상세 화면의 설치 상태 옆에는 "공급사 마지막 확인: 8분 전(폴링)"처럼 **신호의 신선도**도 함께 보여 준다

**왜 중요한가**: 운영자가 30초 전 화면을 보고 "아직 발급 안 됐네"라고 판단해 수동 환불을 누를 수 있다. 데이터가 오래됐다는 것을 보여 주는 것과, 서버가 최신 상태로 다시 확인하는 것이 함께 있어야 한다.

## 6. 캐시를 끈 이유

Next.js App Router는 `fetch` 결과를 캐시할 수 있다(버전마다 기본값이 다름). 결제·발급 상태는 **오래된 값이 보이면 사고**이므로 모든 API 호출에 `cache: 'no-store'`를 명시하고, 페이지에 `export const dynamic = 'force-dynamic'`을 둔다. 요금제 목록은 캐시해도 되지만 단순함을 위해 같은 규칙을 적용했다.

> 2026-10-21 구현 범위: 요금제 → 주문 → 결제 → 발급 대기 → 내 SIM 목록·상세. 환불 버튼, 유심 ICCID 입력, 모의 PG 시연 설정, 어드민 화면은 아직 없다.

| 단계 | 사용자가 하는 일 | 브라우저에서 일어나는 일 | 서버(Next·Spring)에서 일어나는 일 | 파일 |
|---|---|---|---|---|
| 1 | `/`에 들어온다 | (없음) | Next 서버가 `GET /api/plans`로 요금제를 받아 표를 그린 HTML을 보낸다. 쿠키에 아이디가 없으면 주문 버튼을 꺼 둔다 | `app/page.tsx` |
| 2 | 아이디를 입력하고 [저장] | 쿠키 `roampass_user`에 저장 → `router.refresh()` | 페이지가 서버에서 다시 실행되어 "OOO님"과 켜진 주문 버튼을 그린다 | `components/UserIdForm.tsx` |
| 3 | 요금제·여행 시작일을 고르고 [주문하기] | `POST /api/orders` (요청 중 버튼 비활성) → 성공하면 `/checkout/주문번호`로 이동 | Spring이 PENDING 주문을 만든다. 여행 시작일 기본값·최솟값은 서버가 계산한 **KST 오늘** | `features/order/components/OrderForm.tsx` |
| 4 | 결제 화면을 본다 | (없음) | 서버가 내 주문을 조회해 금액·결제 기한(KST)을 그린다. 남의 주문이면 404 화면 | `app/checkout/[orderNo]/page.tsx` |
| 5 | [결제하기] | 화면이 처음 그려질 때 만든 **멱등키**를 붙여 `POST /api/orders/{no}/payments`. 승인·결과 모름(READY)이면 대기 화면으로, 거절이면 메시지 + 새 멱등키 | Spring이 PG를 부르고 결제를 확정한다 → 커밋 후 발급 시작(서버 책임) | `features/payment/components/PayButton.tsx` |
| 6 | 대기 화면에서 기다린다 | 서버가 준 첫 상태로 시작해서 **2초마다** `GET /api/my/orders/{no}`. 최종 상태(발급 완료·실패·환불 등)면 멈춘다. 30초가 지나면 "평소보다 오래 걸려요" 안내 | 발급은 브라우저와 상관없이 서버가 진행한다. 창을 닫아도 된다 | `features/order/components/IssueStatusPoller.tsx` |
| 7 | [내 SIM에서 설치 코드 보기] | `/my-sims/주문번호`로 이동 | 서버가 주문과 SIM 정보를 **동시에** 조회한다. SIM이 아직 없으면(404) "아직 발급 전"으로 보여 준다 | `app/my-sims/[orderNo]/page.tsx` |
| 8 | [설치 코드 보기] | `POST .../profile/qr-view` → **그 응답으로 받은** 코드를 보여 주고 `router.refresh()`. 페이지는 코드를 미리 브라우저로 보내지 않는다 | Spring이 처음 본 시각을 기록한다(ISSUED → QR_VIEWED). 두 번째부터는 그대로 | `features/issue/components/QrReveal.tsx` |
| 9 | [설치 상태 다시 확인] | `POST .../profile/refresh` → `router.refresh()` | Spring이 공급사에 바로 물어보고 설치·개통을 반영한다. 개통이면 만료 시각 = 개통 + 일수 × 24h | `features/issue/components/RecheckButton.tsx` |
| 10 | 헤더의 [내 SIM] | (없음) | 서버가 `GET /api/my/orders`로 내 주문 목록(최신순)을 그린다. 아이디가 없으면 `/`로 보낸다 | `app/my-sims/page.tsx` |

### `router.refresh()`가 하는 일
버튼(Client Component)이 서버 데이터를 바꾼 뒤 부른다. 페이지 전체를 새로 받지 않고, **그 페이지의 Server Component 부분만 서버에서 다시 실행**해 바뀐 부분을 갈아 끼운다. 버튼이 화면 위쪽 상태 글자를 직접 고칠 필요가 없어서, "화면은 항상 서버 데이터 기준"이라는 규칙이 지켜진다.

### 직접 확인한 것 (헤드리스 Chrome으로 클릭)
- 아이디가 없으면 주문 버튼 비활성 → 저장하면 켜짐
- 주문 → 결제 → **결제 버튼 더블클릭** → 대기 화면 → 폴링으로 "발급 완료" → 내 SIM → 설치 코드 보기(QR_VIEWED) → 공급사 개통 후 다시 확인 → "사용 중", 개통 2026-05-02 00:20 / 만료 2026-05-05 00:20 (KST, 3일 요금제)
- 더블클릭해도 결제 요청(READY 생성)은 1건
- 남의 주문 상세 404, 아이디 없이 `/my-sims` → `/`

### 어드민 화면 동작 (2026-10-21 구현)

| 사용자가 하는 일 | 일어나는 일 | 파일 |
|---|---|---|
| `/admin`에 들어온다 | 페이지(Server)가 URL 쿼리를 읽어 `GET /api/admin/orders?...&page=&size=20`을 부르고 표를 그린다 | `app/admin/page.tsx` |
| 필터를 고르고 [조회] | 폼(Client)은 데이터를 가져오지 않고 **URL만 바꾼다**(`router.push('/admin?orderStatus=ISSUED')`). 페이지가 새 URL로 서버에서 다시 실행된다. 필터를 바꾸면 첫 페이지로 | `features/admin/components/AdminFilters.tsx` |
| [다음 →] | 그냥 링크다(`/admin?…&page=1`). 지금 필터를 유지한 주소를 서버가 만들어 둔다 | `app/admin/page.tsx` |
| 가만히 본다 | "N초 전 데이터"가 1초마다 늘어난다(응답의 `fetchedAt` 기준, 60초가 넘으면 노란색) | `components/FreshnessBadge.tsx` |
| [새로고침] / 자동 새로고침 켜기 | `router.refresh()`(10초마다) → 서버가 다시 조회 → 새 `fetchedAt`으로 "0초 전"부터 다시 센다 | `features/admin/components/RefreshControls.tsx` |
| 주문번호 클릭 | 상세(Server)가 `GET /api/admin/orders/{no}`로 주문·결제·SIM 정보와 타임라인을 그린다. 타임라인은 초까지, 발생과 기록이 1분 넘게 차이 나면 두 시각 모두 | `app/admin/orders/[orderNo]/page.tsx` |

직접 확인(헤드리스 Chrome): 총 54건 3페이지 이동, 주문 ISSUED + 설치 ACTIVE 필터 → URL 반영·새로고침해도 유지, [초기화] 후 폼도 비워짐, 미래 기간 0건, "2초 전" → [새로고침] → "0초 전", 상세 타임라인 7줄(주문 생성 → 결제 요청 → PG 승인 → 결제 승인 → 발급 요청 → 발급 완료 → 개통), 없는 주문 404

## 8. 한계

- 대기 화면 사용자가 많으면 2초 폴링 요청이 쌓인다. 개선 방향은 간격을 점점 늘리는 것(2초 → 5초 → 10초)이나 SSE다
- 인증이 쿠키에 담긴 아이디 문자열뿐이다(과제 범위 밖). 쿠키 값을 바꾸면 다른 사용자로 행세할 수 있다. 아이디는 헤더로 가서 영문·숫자·`_-`만 받는다
- 내 SIM 목록(`GET /api/my/orders`)에 페이지가 없다. 한 사람의 주문이 많지 않다고 보고 전부 돌려준다
- UI는 기본 HTML 수준이다(평가 항목 아님)

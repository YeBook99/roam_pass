## D-001 큰 틀 스택 (2026-10-20)
- 결정: Next.js / Spring Boot / MySQL 8 (과제가 Next.js · Spring · 관계형 DB를 지정)
- 왜: MySQL은 익숙해서. 필요한 기능(유니크 제약, 트랜잭션, `FOR UPDATE SKIP LOCKED`)이 MySQL 8에 다 있다
- 버린 것: PostgreSQL (회사가 쓰지만 새 DB 학습보다 정합성 설계에 시간을 쓰기로)
- 한계: `DATETIME`에 시간대가 없음 → UTC 저장 규칙(I10)으로 보완. 부분 유니크 인덱스 없음 → `dedupe_key` 컬럼으로 대체

## D-002 백엔드 언어 · 빌드 (2026-10-20)
- 결정: Java 21 + Gradle wrapper
- 왜: 로컬에 JDK 21이 있고 자료가 가장 많음. wrapper라 리뷰어 PC에 Gradle 설치 불필요
- 버린 것: Kotlin (새 언어 학습 비용), Maven
- 한계: —

## D-003 비동기 작업 방식 (2026-10-20)
- 결정: DB 작업 테이블 + `@Scheduled` 폴러 + `SKIP LOCKED`
- 왜: 상태 변경과 "다음에 할 일"을 같은 트랜잭션에 저장 → 서버가 죽거나 잠들어도 유실 없음. 추가 인프라 0
- 버린 것: Kafka / RabbitMQ / Redis 큐 (무료 배포 부담, DB 저장과 발행이 따로 놀아 이중 쓰기 문제), `@Async` (재시작 시 유실)
- 한계: 폴링 주기만큼 지연, 작업이 아주 많아지면 DB 부하 → GUIDE §7.8, 인터뷰 "10만 개" 질문

## D-004 모의 PG · 공급사 위치 (2026-10-20)
- 결정: 같은 Spring 앱의 별도 패키지, 우리 서비스와는 HTTP로만 대화, 자기 전용 테이블 사용
- 왜: 배포 대상 1개로 단순화하면서도 타임아웃 · 5xx · 지연 콜백을 진짜 HTTP로 재현
- 버린 것: 별도 서버 (배포 2배), 메서드 직접 호출 (네트워크 실패를 흉내 못 냄)
- 한계: 같은 JVM이라 우리 앱이 죽으면 모의 서버도 같이 죽음 (실제로는 독립 장애)

## 0. 한 줄 비유

> **상태 선점 = 의자 뺏기 놀이.** 의자(처리권)는 하나뿐이고, 음악이 멈추는 순간 여러 명이 동시에 앉으려 해도 **실제로 앉는 사람은 한 명**이다. 심판(DB)이 누가 먼저 앉았는지 판정해 준다.

## 1. 경쟁 상태(race condition)

**두 개 이상의 작업이 같은 데이터를 동시에 다룰 때, 실행 순서에 따라 결과가 달라지는 상황**을 말한다.

### 예: 운영자 두 명이 동시에 환불 버튼을 누름
```
시각   운영자 A (스레드 1)              운영자 B (스레드 2)
t1     주문 조회 → 상태 ISSUED
t2                                     주문 조회 → 상태 ISSUED
t3     "ISSUED니까 환불 가능" 판단
t4                                     "ISSUED니까 환불 가능" 판단
t5     PG 취소 호출 (10,000원)
t6                                     PG 취소 호출 (10,000원)   ← 💥 두 번 환불
t7     상태 REFUNDED 저장
t8                                     상태 REFUNDED 저장
```
각 스레드는 **자기 입장에서는 올바르게** 동작했다. 문제는 t1과 t5 사이, 즉 **"확인"과 "실행" 사이에 틈이 있다**는 점이다. 이 틈에 다른 스레드가 끼어든다.

### 이 과제에서 경쟁 상태가 생기는 곳
- PG 승인 응답과 웹훅이 동시에 도착 → 결제 두 번 처리
- 공급사 콜백 N개가 동시에 도착 → 프로필 두 번 저장
- 이벤트 처리와 스케줄러가 같은 주문을 동시에 발급 요청
- 운영자 두 명의 동시 조치
- 결제 만료 스케줄러와 늦게 온 승인

## 2. 멱등성(idempotency)

**같은 요청을 1번 하든 N번 하든 결과가 같은 성질**을 말한다.

| 멱등 ✅ | 멱등 아님 ❌ |
|---|---|
| "주문 1번의 상태를 PAID로 만들어라" | "잔액에서 1,000원 빼라" |
| "전등을 켜라" | "전등 스위치를 눌러라(토글)" |
| `PUT /users/1 {name: "kim"}` | `POST /orders` (누를 때마다 새 주문) |

### 왜 필요한가
네트워크는 믿을 수 없다. 요청을 보냈는데 응답이 안 오면 **"처리됐는지 안 됐는지 모른다"**. 안전하게 다시 보내려면 다시 보내도 문제가 없어야 하고, 그 성질이 멱등성이다. PG와 공급사가 웹훅·콜백을 **여러 번 보내는 것도** 받는 쪽(우리)이 멱등하다는 전제가 있기 때문이다.

### 멱등키(Idempotency Key)
원래 멱등하지 않은 요청(결제 생성)을 멱등하게 만드는 방법이다. 요청에 **"이 요청의 고유 번호"**를 붙이고, 서버는 같은 번호의 요청을 두 번째부터는 **새로 처리하지 않고 첫 결과를 돌려준다**.

```
1차: POST /payments  Idempotency-Key: abc-123  → 결제 생성, 결과 R 저장
2차: POST /payments  Idempotency-Key: abc-123  → "이미 처리한 abc-123이네" → 결과 R 반환
```
이 과제에서는 `payment.idempotency_key UNIQUE`로 구현한다(`06` §6).

## 3. 상태 선점

### 3.1 정의
> **"현재 상태가 A일 때만 B로 바꿔라"를 확인과 변경을 분리하지 않고 SQL UPDATE 한 문장으로 DB에 맡기는 것.**
> UPDATE가 바꾼 행의 수가 1이면 **내가 처리권을 차지(선점)했다**는 뜻이고, 0이면 **다른 누군가가 이미 차지했다**는 뜻이다.

```sql
UPDATE sim_order
   SET status = 'REFUNDING'
 WHERE id = 1
   AND status = 'ISSUED';      -- ← 이 조건이 핵심
-- 결과: 1 row updated → 내가 환불 담당
--       0 rows updated → 이미 누가 바꿨음 → 아무것도 하지 않고 종료
```

### 3.2 왜 이게 안전한가 — 1절의 "틈"이 사라진다
"확인(status가 ISSUED인가?)"과 "변경(REFUNDING으로)"이 **한 문장**이라 그 사이에 끼어들 틈이 없다.

```
시각   운영자 A                                    운영자 B
t1     UPDATE ... WHERE status='ISSUED'
       → DB가 1번 행을 잠금, 상태 변경 → 1 row
t2                                                UPDATE ... WHERE status='ISSUED'
                                                  → 1번 행이 A에게 잠겨 있어 **대기**
t3     COMMIT (잠금 해제)
t4                                                대기 끝 → 행을 다시 확인: 상태가 이제 REFUNDING
                                                  → WHERE 조건 불일치 → **0 rows**
t5     PG 취소 호출 (A만)                          "이미 처리 중입니다" 응답
```

PostgreSQL의 동작(기본 격리 수준 READ COMMITTED)을 정리하면 이렇다.
- 같은 행을 UPDATE하려는 두 번째 트랜잭션은 첫 번째가 끝날 때까지 **기다린다**(행 수준 잠금)
- 첫 번째가 커밋하면, 두 번째는 **바뀐 최신 행을 기준으로 WHERE 조건을 다시 평가**한다
- 조건이 더 이상 맞지 않으므로 0행이 된다

잠금은 **UPDATE 한 문장이 실행되고 트랜잭션이 끝날 때까지만** 유지된다. 그래서 외부 호출을 트랜잭션 밖에 두면 잠금 시간이 매우 짧다(`06` §1).

### 3.3 JPA로 쓰는 법
```java
public interface SimOrderRepository extends JpaRepository<SimOrder, Long> {

    @Modifying(clearAutomatically = true, flushAutomatically = true)
    @Query(value = """
        UPDATE sim_order
           SET status = :to, updated_at = now()
         WHERE id = :id AND status = :from
        """, nativeQuery = true)
    int updateStatusIf(@Param("id") Long id, @Param("from") String from, @Param("to") String to);
}
```
- `@Modifying`: "이 쿼리는 SELECT가 아니라 데이터를 바꾼다"는 표시다. 반환값 `int`가 **영향 받은 행 수**다
- `clearAutomatically = true`: 실행 후 JPA의 1차 캐시(영속성 컨텍스트)를 비운다. 그래야 다음에 엔티티를 조회할 때 바뀐 값을 읽는다
- `flushAutomatically = true`: 실행 전에 아직 DB에 안 보낸 변경을 먼저 보낸다
- 반드시 `@Transactional` 안에서 호출한다

### 3.4 흔한 잘못: JPA로 "조회 → 판단 → 저장"
```java
@Transactional
public void refund(Long id) {
    SimOrder o = repo.findById(id).orElseThrow();   // SELECT
    if (o.getStatus() != ISSUED) return;             // 판단  ← 여기서 다른 스레드도 ISSUED를 봄
    o.setStatus(REFUNDING);                           // 변경 (커밋 때 UPDATE ... WHERE id=? — 상태 조건 없음!)
    pgClient.cancel(...);                             // 💥 두 스레드 모두 실행
}
```
JPA가 커밋할 때 만드는 UPDATE에는 `AND status='ISSUED'` 조건이 없다. 그래서 둘 다 성공한다. 이것을 막으려면 락(§5)을 쓰거나 **상태 선점**을 써야 한다.

## 4. UNIQUE 제약과 `ON CONFLICT DO NOTHING`

### 4.1 UNIQUE 제약
"이 컬럼(들)의 값은 테이블 전체에서 하나뿐이어야 한다"는 DB 규칙이다. 두 번째 INSERT는 **에러**가 난다.

### 4.2 `ON CONFLICT DO NOTHING` (PostgreSQL)
에러를 내는 대신 **조용히 아무것도 하지 않고 0행을 반환**한다.

```java
@Modifying
@Query(value = """
    INSERT INTO callback_log (source, event_key, payload, signature_ok, created_at, updated_at)
    VALUES (:source, :eventKey, :payload, true, :now, :now)
    ON CONFLICT (event_key) DO NOTHING
    """, nativeQuery = true)
int insertIgnore(@Param("source") String source, @Param("eventKey") String eventKey, @Param("payload") String payload);
// 1 → 처음 받은 이벤트 → 처리 계속 / 0 → 이미 받은 이벤트 → 중복이므로 종료
```

**에러(예외) 방식보다 나은 이유**: 같은 트랜잭션에서 UNIQUE 위반 예외가 나면 PostgreSQL은 그 트랜잭션 전체를 "실패" 상태로 만든다. 이후 쿼리가 모두 거부된다. `ON CONFLICT`는 예외가 아니므로 트랜잭션이 깨끗하게 유지된다.

### 4.3 동시에 같은 키로 INSERT하면?
상태 선점과 비슷하게 동작한다. 두 번째 INSERT는 첫 번째 트랜잭션이 끝날 때까지 기다린다.
- 첫 번째가 **커밋** → 두 번째는 충돌 → 0행
- 첫 번째가 **롤백** → 두 번째가 INSERT 성공 → 1행 (처리를 이어받음)

### 4.4 NULL은 중복으로 안 친다
UNIQUE 컬럼에 NULL은 여러 개 들어갈 수 있다. 그래서 서명이 틀린 콜백은 `event_key = NULL`로 저장한다. 위조 요청이 정상 키를 "선점"하지 못하게 하기 위해서다(`05` §9).

## 5. 락(lock) 비교 — 왜 안 썼나

| 방식 | 코드 | 동작 | 이 과제에서 |
|---|---|---|---|
| **비관적 락** | `@Lock(PESSIMISTIC_WRITE)` → `SELECT ... FOR UPDATE` | 읽는 순간 잠근다. 다른 트랜잭션은 내가 끝날 때까지 대기 | ❌ 잠근 채 PG를 호출하면 그동안 모두 대기. 데드락 위험 |
| **낙관적 락** | 엔티티에 `@Version Long version` | 저장할 때 `WHERE version=?`. 버전이 바뀌었으면 `OptimisticLockException` | ❌ 상태 선점과 원리가 같지만 예외 처리·재시도 코드가 필요 |
| **분산 락** | Redis `SET NX` 등 | 외부 저장소로 락 | ❌ 인프라 추가 |
| **상태 선점** | 조건부 UPDATE | 바꿀 때 조건 확인 | ✅ |

> 상태 선점은 사실 **"상태 컬럼을 버전처럼 쓰는 낙관적 락"**이라고 볼 수 있다. 차이는 예외 대신 **영향 행 수(0/1)**로 결과를 받아서, "이미 처리됨"을 정상 흐름으로 다룰 수 있다는 점이다.

## 6. 트랜잭션과 격리 수준 (최소한만)

- **트랜잭션**: 여러 쿼리를 "전부 성공 아니면 전부 취소"로 묶은 단위
- **격리 수준**: 동시에 실행되는 트랜잭션끼리 서로의 변경을 얼마나 볼 수 있는지 정하는 수준. PostgreSQL 기본값은 **READ COMMITTED**로, "커밋된 것만 보인다"는 뜻이다
- 이 과제는 격리 수준을 올리지 않는다(SERIALIZABLE 등). 대신 **상태 선점과 UNIQUE 제약**으로 필요한 지점만 정확히 막는다. 격리 수준을 올리면 충돌 시 재시도 코드가 필요하고 성능도 떨어진다

## 7. HMAC 서명 — "이 콜백은 진짜 공급사가 보냈나?"

### 7.1 문제
`/api/webhooks/supplier`는 인터넷에 공개된 주소다. 누구나 `{ "supplierOrderNo": "...", "iccid": "..." }`를 보낼 수 있다. 서명을 확인하지 않으면 **가짜 콜백으로 발급 완료 처리**를 할 수 있다(2.7 감점 항목).

### 7.2 HMAC이란
> **비유: 우리와 공급사만 아는 도장(비밀키)으로 편지(본문)에 찍은 봉인.** 편지를 한 글자라도 고치면 봉인이 맞지 않고, 도장이 없는 사람은 봉인을 만들 수 없다.

```
공급사: signature = HMAC-SHA256(본문, 공유 비밀키)  → 헤더 X-Signature에 담아 전송
우리:   expected  = HMAC-SHA256(받은 본문, 같은 비밀키)
        expected == X-Signature ?  → 진짜이고 변조되지 않음
```
- **해시(SHA-256)만 쓰면 안 되는 이유**: 해시는 누구나 계산할 수 있다. 공격자가 본문을 고치고 해시를 다시 계산하면 끝이다. HMAC은 **비밀키가 있어야만** 계산할 수 있다

### 7.3 코드
```java
public boolean verify(byte[] rawBody, String signatureHeader) {
    Mac mac = Mac.getInstance("HmacSHA256");
    mac.init(new SecretKeySpec(secret.getBytes(UTF_8), "HmacSHA256"));
    byte[] expected = mac.doFinal(rawBody);
    byte[] actual = HexFormat.of().parseHex(signatureHeader);
    return MessageDigest.isEqual(expected, actual);   // 고정 시간 비교
}
```

### 7.4 주의점 세 가지
1. **원문 바이트 그대로 계산한다.** 컨트롤러에서 `@RequestBody SupplierCallback dto`로 받으면 원문이 사라진다. `@RequestBody byte[] body`(또는 `String`)로 받아 먼저 검증한 뒤 JSON으로 변환한다. JSON을 객체로 바꿨다가 다시 문자열로 만들면 공백이나 필드 순서가 달라져 서명이 맞지 않는다
2. **`equals` 대신 `MessageDigest.isEqual`을 쓴다.** 일반 비교는 다른 글자를 만나는 순간 멈추므로, 응답 시간 차이로 서명을 한 글자씩 추측하는 공격(타이밍 공격)이 이론상 가능하다
3. **비밀키는 환경변수로** 받는다. 저장소에 커밋하지 않는다(2.7 감점 항목)

### 7.5 한계: 재전송 공격
서명이 맞는 진짜 콜백을 가로채 **그대로 다시 보내면** 서명은 여전히 맞는다. 이 과제에서는 `event_key` 중복 방지로 두 번 처리되지 않게 막는다. 실무에서는 서명에 타임스탬프를 포함해서 5분 이상 지난 요청을 거절한다.

## 8. 면접에서 말하는 법

> "중복 처리를 막을 때 제가 가장 많이 쓴 건 '상태 선점'입니다. 상태가 PENDING일 때만 PAID로 바꾸라는 UPDATE를 한 문장으로 보내고, 바뀐 행이 1이면 제가 처리하고 0이면 이미 누가 처리한 걸로 보고 끝냅니다. 확인과 변경 사이에 틈이 없어서, 웹훅 20개가 동시에 와도 DB가 한 줄로 세워 한 번만 통과시킵니다.
> 같은 이벤트가 여러 번 오는 건 event_key에 UNIQUE를 걸고 `ON CONFLICT DO NOTHING`으로 처리했고, 공급사 콜백은 HMAC 서명이 맞을 때만 받습니다."

### 스스로 점검
- [ ] "조회 → if문 → 저장"이 왜 경쟁 상태를 만드는지 타임라인으로 그릴 수 있다
- [ ] 조건부 UPDATE에서 두 번째 트랜잭션이 왜 0행이 되는지 "잠금 대기 → 재평가"로 설명할 수 있다
- [ ] 멱등키를 클릭마다 새로 만들면 왜 안 되는지 말할 수 있다
- [ ] 해시와 HMAC의 차이를 말할 수 있다
- [ ] 서명 검증에 원문 바이트가 필요한 이유를 말할 수 있다

# L4. 동시성 테스트 도구 — ExecutorService, CountDownLatch, Testcontainers, Awaitility

> 목표: "같은 통지 N개를 **동시에** 보냈을 때 1번만 처리된다"를 **증명하는 테스트**를 직접 작성하고 설명할 수 있게 된다 (질문 3, 제출물 5)
> 관련 문서: `11_테스트_전략.md`

---

## 0. 한 줄 비유

> - **ExecutorService** = 달리기 선수단(스레드풀). 일을 던지면 선수들이 나눠서 뛴다
> - **CountDownLatch** = 출발 신호총과 결승선 기록원. "모두 준비됐나? → 탕! → 모두 들어왔나?"

---

## 1. 왜 for문 20번은 동시성 테스트가 아닌가

```java
for (int i = 0; i < 20; i++) confirmService.confirm(webhook);   // ❌
```
이 코드는 **하나의 스레드가 순서대로** 20번 호출한다. 두 번째 호출은 첫 번째가 **완전히 끝난 뒤** 시작하므로 경쟁 상태가 생길 수 없다. 조건부 UPDATE 없이 "조회 → if → 저장"으로 짜도 이 테스트는 통과한다. 즉 **아무것도 증명하지 못한다**.

동시성 테스트는 여러 스레드가 **같은 순간에** 같은 코드에 들어가게 만들어야 한다.

## 2. ExecutorService — 여러 스레드에 일을 던지는 도구

Java 표준 라이브러리(`java.util.concurrent`)에 있다.

```java
ExecutorService pool = Executors.newFixedThreadPool(20);  // 스레드 20개짜리 풀

Future<String> f = pool.submit(() -> {                     // 일을 던짐 (다른 스레드에서 실행됨)
    return "결과";
});

String result = f.get();       // 그 일이 끝날 때까지 기다렸다가 결과를 받음
pool.shutdown();               // 다 쓰면 반드시 종료 (안 하면 스레드가 남음)
```

| 메서드 | 의미 |
|---|---|
| `Executors.newFixedThreadPool(n)` | 스레드 n개를 가진 풀 생성 |
| `submit(Callable)` | 값을 반환하는 일 제출 → `Future` 반환 |
| `submit(Runnable)` / `execute(Runnable)` | 값이 없는 일 제출 |
| `Future.get()` | 결과 대기. 그 스레드에서 예외가 났다면 **`ExecutionException`으로 다시 던져 줌** |
| `shutdown()` | 새 일을 받지 않고, 하던 일이 끝나면 종료 |

> **`execute()` 대신 `submit()` + `Future.get()`을 쓰는 이유**: `execute()`로 던진 일에서 예외가 나면 그 스레드에서 로그만 찍히고 **테스트는 모른 채 통과**할 수 있다. `Future.get()`은 예외를 테스트 스레드로 다시 던져 주므로 실패가 드러난다.

### 그런데 submit만으로는 "동시에" 시작하지 않는다
`submit`을 20번 하는 동안 먼저 제출된 일은 이미 실행을 시작해 끝나 버릴 수 있다. 출발선을 맞춰야 한다 → **CountDownLatch**

## 3. CountDownLatch — 숫자를 세는 관문

```java
CountDownLatch latch = new CountDownLatch(3);   // 숫자 3에서 시작
latch.countDown();   // 3 → 2
latch.countDown();   // 2 → 1
latch.countDown();   // 1 → 0  → 관문이 열림
latch.await();       // 0이 될 때까지 이 줄에서 멈춰 기다림 (이미 0이면 바로 통과)
```
- 숫자는 내려가기만 하고 다시 올릴 수 없다(일회용)
- `await(10, SECONDS)`: 최대 10초만 기다린다. 시간 안에 열리면 `true`를 반환한다 → 테스트가 영원히 멈추는 것을 방지

### 3개 래치 패턴 — "진짜 동시에" 출발시키기

```
ready (N): 각 선수가 "준비됐어요" 할 때마다 -1 → 메인이 모두 준비될 때까지 기다림
start (1): 메인이 "탕!" 하면 0 → 모든 선수가 동시에 출발
done  (N): 각 선수가 끝날 때마다 -1 → 메인이 모두 끝날 때까지 기다림
```

```
메인 스레드                   스레드 1..20
──────────                   ───────────────
                              ready.countDown()   ("준비 완료")
                              start.await()       (출발 신호 대기 ⏸)
ready.await()  ⏸ (20명 대기)
start.countDown() → "탕!" 🔫
                              ▶ 20개가 거의 동시에 confirm() 진입
                              done.countDown()
done.await()  ⏸ (20명 완료 대기)
결과 검증
```

## 4. 전체 예제 — 같은 승인 웹훅 20개 동시 처리

```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@Testcontainers
@TestPropertySource(properties = {
    "app.scheduling.enabled=false",                     // 스케줄러는 끄고 테스트가 통제
    "spring.datasource.hikari.maximum-pool-size=30"     // 스레드 수보다 커넥션이 적으면 줄 서서 기다림
})
class PaymentWebhookConcurrencyTest {

    @Container
    @ServiceConnection                                    // Boot 3.1+: 컨테이너 접속 정보를 datasource에 자동 연결
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16-alpine");

    @Autowired PaymentConfirmService confirmService;
    @Autowired PaymentRepository paymentRepository;
    @Autowired StatusHistoryRepository historyRepository;
    @Autowired TestFixtures fixtures;
    @Autowired MockSupplierProbe supplierProbe;           // 모의 공급사가 받은 요청 수를 세는 테스트 도우미

    @Test
    void 같은_승인_웹훅_20개를_동시에_보내도_결제는_한번만_처리된다() throws Exception {
        // given: 결제 대기 주문과 READY 결제
        SimOrder order = fixtures.pendingOrderWithReadyPayment(10_000);
        PgResult webhook = PgResult.approved(order.getOrderNo(), "PG-TID-1", 10_000);

        int n = 20;
        ExecutorService pool = Executors.newFixedThreadPool(n);
        CountDownLatch ready = new CountDownLatch(n);
        CountDownLatch start = new CountDownLatch(1);
        CountDownLatch done  = new CountDownLatch(n);
        List<Future<ConfirmResult>> futures = new ArrayList<>();

        // when: 20개 스레드가 출발선에 섬
        for (int i = 0; i < n; i++) {
            futures.add(pool.submit(() -> {
                ready.countDown();
                start.await();                              // 출발 신호 대기
                try {
                    return confirmService.confirm(webhook, Signal.WEBHOOK);
                } finally {
                    done.countDown();
                }
            }));
        }
        ready.await();                                      // 20개 모두 준비될 때까지
        start.countDown();                                  // 🔫 동시에 출발
        assertThat(done.await(10, TimeUnit.SECONDS)).isTrue();
        pool.shutdown();

        List<ConfirmResult> results = new ArrayList<>();
        for (Future<ConfirmResult> f : futures) results.add(f.get());   // 스레드 안 예외가 있으면 여기서 터짐

        // then: 관찰 가능한 결과를 센다
        assertThat(results).filteredOn(r -> r == ConfirmResult.PROCESSED).hasSize(1);
        assertThat(results).filteredOn(r -> r == ConfirmResult.DUPLICATE).hasSize(n - 1);
        assertThat(paymentRepository.countByOrderIdAndStatus(order.getId(), PaymentStatus.APPROVED)).isEqualTo(1);
        assertThat(historyRepository.countOrderTransition(order.getId(), "PENDING", "PAID")).isEqualTo(1);

        // 발급 요청은 비동기(@Async)라서 잠시 기다렸다가 확인
        await().atMost(Duration.ofSeconds(5))
               .untilAsserted(() -> assertThat(supplierProbe.issueRequestCount(order.getOrderNo())).isEqualTo(1));
    }
}
```

### 무엇을 검증하나 (`assertTrue(true)`가 아닌 이유)
| assert | 의미 |
|---|---|
| PROCESSED가 1개 | 20개 중 **딱 하나만** 처리권을 얻었다 |
| DUPLICATE가 19개 | 나머지는 **에러 없이** 중복으로 걸러졌다 |
| APPROVED 결제 1행 | DB에 남은 결과가 하나다 |
| PENDING→PAID 이력 1행 | 상태 전이가 한 번만 일어났다 |
| 공급사 발급 요청 1회 | 결제가 한 번만 처리됐으므로 **발급도 한 번만** 나갔다(돈과 SIM 양쪽 확인) |

## 5. ⚠️ 동시성 테스트에 `@Transactional`을 붙이면 안 된다

Spring 테스트에서 테스트 메서드에 `@Transactional`을 붙이면, 테스트가 끝날 때 **롤백**되어 데이터가 깔끔하게 정리된다. 편하지만 **동시성 테스트에서는 함정**이다.

- `given`에서 만든 주문은 **테스트 스레드의 트랜잭션 안**에 있고 아직 커밋되지 않았다
- `ExecutorService`의 다른 스레드들은 **각자 다른 트랜잭션**이다. READ COMMITTED에서는 커밋되지 않은 데이터를 볼 수 없다
- 결과: 다른 스레드들이 주문을 못 찾아 **테스트가 엉뚱한 이유로 실패하거나, 아무것도 처리하지 않고 통과**한다

**해결**: 동시성 테스트 클래스에는 `@Transactional`을 붙이지 않는다. 데이터를 실제로 커밋하고, `@AfterEach`(또는 `@BeforeEach`)에서 `TRUNCATE ... RESTART IDENTITY CASCADE`로 정리한다.

## 6. Testcontainers — 테스트할 때 진짜 PostgreSQL 띄우기

- 테스트가 시작되면 **Docker로 PostgreSQL 컨테이너를 자동으로 띄우고**, 끝나면 지운다
- 그래서 **Docker Desktop이 실행 중이어야** 한다(README 실행 방법에 명시)
- `@ServiceConnection`(Spring Boot 3.1+)을 붙이면 컨테이너의 주소, 포트, 계정을 `spring.datasource.*`에 자동으로 연결해 준다
- Flyway가 빈 DB에 스키마를 만든다. 운영과 **같은 마이그레이션 파일**로 테스트하는 셈이다

```groovy
// build.gradle (의존성)
testImplementation 'org.springframework.boot:spring-boot-testcontainers'
testImplementation 'org.testcontainers:junit-jupiter'
testImplementation 'org.testcontainers:postgresql'
testImplementation 'org.awaitility:awaitility'
```

**H2 대신 쓰는 이유**: H2는 `ON CONFLICT`, 부분 유니크 인덱스, 행 잠금 동작이 PostgreSQL과 다르다. 이 과제의 중복 방지는 **DB 기능에 의존**하므로 다른 DB로 테스트하면 결과를 믿을 수 없다(ADR-11).

## 7. Awaitility — 비동기 결과를 "기다렸다가" 확인

`@Async`로 실행되는 발급 요청은 `confirm()`이 반환된 **뒤에** 일어난다. 바로 assert하면 아직 실행 전이라 실패한다.

```java
// ❌ 나쁜 방법
Thread.sleep(3000);                 // 너무 짧으면 실패, 길면 테스트가 느려짐
assertThat(count).isEqualTo(1);

// ✅ Awaitility
await().atMost(Duration.ofSeconds(5))          // 최대 5초까지
       .pollInterval(Duration.ofMillis(100))   // 100ms마다 다시 확인
       .untilAsserted(() -> assertThat(probe.count()).isEqualTo(1));   // 통과하는 순간 바로 다음으로
```

## 8. 이 테스트가 정말 의미 있는지 확인하는 법 (꼭 해 볼 것)

**일부러 코드를 망가뜨려서 테스트가 실패하는지 본다.**
1. `updateStatusIf`의 `AND status = :from` 조건을 잠시 지운다
2. `callback_log`의 `ON CONFLICT`를 잠시 지운다(또는 event_key를 매번 다르게)
3. 테스트를 돌려 **PROCESSED가 2개 이상** 나오며 실패하는지 확인한다
4. 원래대로 되돌린다

이 과정을 거쳐야 "테스트가 실제로 중복을 잡아낸다"고 말할 수 있다. 인터뷰에서 **"조건을 빼고 돌려 보니 처리가 3번 됐고, 넣으니 1번이 됐습니다"**라고 말할 수 있으면 아주 강한 근거가 된다.

> ✍️ 직접 해 보고 결과를 적기: 조건 제거 시 PROCESSED 개수 = ___ / 복구 후 = 1

## 9. 자주 하는 실수

| 실수 | 결과 | 해결 |
|---|---|---|
| for문으로 순서대로 호출 | 경쟁 상태가 없어 무조건 통과 | ExecutorService + CountDownLatch |
| `execute()` 사용, `Future.get()` 안 함 | 스레드 안 예외를 놓침 | `submit()` + `get()` |
| 테스트에 `@Transactional` | 다른 스레드가 데이터를 못 봄 | 붙이지 않고 TRUNCATE로 정리 |
| `done.await()` 없이 검증 | 스레드가 끝나기 전에 assert | `done.await(타임아웃)` |
| 커넥션 풀이 스레드보다 작음 | 동시성이 줄어듦(줄 서기) | 테스트에서 풀 크기 확대 |
| `Thread.sleep`으로 비동기 대기 | 불안정하거나 느림 | Awaitility |
| `pool.shutdown()` 누락 | 스레드 누수 | finally에서 shutdown |

## 10. 면접에서 말하는 법

> "for문으로 20번 부르면 순서대로 실행돼서 동시성 테스트가 안 됩니다. 그래서 ExecutorService로 스레드 20개를 만들고, CountDownLatch로 20개가 모두 준비될 때까지 붙잡아 뒀다가 한 번에 출발시켰습니다.
> 검증은 '에러가 안 났다'가 아니라 결과를 셌습니다. 처리 성공 1개, 중복 19개, 승인 결제 1행, 상태 이력 1줄, 그리고 공급사 발급 요청도 1번인지 확인했습니다.
> 이 테스트가 진짜 의미 있는지 보려고 조건부 UPDATE의 조건을 일부러 빼고 돌려 봤는데 ✍️(N)번 처리되면서 실패했습니다."

### 스스로 점검
- [ ] for문 테스트가 왜 의미 없는지 설명할 수 있다
- [ ] 3개 래치(ready/start/done) 각각의 역할을 말할 수 있다
- [ ] 동시성 테스트에 `@Transactional`을 붙이면 무슨 일이 생기는지 설명할 수 있다
- [ ] H2가 아니라 Testcontainers를 쓴 이유를 말할 수 있다
- [ ] 일부러 망가뜨려 테스트가 실패하는 것을 직접 확인했다

# 05. 정합성과 멱등성 (질문 3)

> 질문 3: 같은 결제 통지 N개, 같은 공급사 콜백 N개를 **동시에** 보냈을 때 결제 1번, 프로필 1개만 남는 테스트가 있어야 합니다. 어떤 방법(유니크 제약 / 조건부 업데이트 / 락 등)을 골랐고 나머지를 **왜 버렸는지**, 실제 실행 결과와 함께 적어 주세요.

먼저 읽을 것: [L3 동시성 핵심 개념](learn/L3_동시성_핵심개념.md). 이 문서에 나오는 멱등성, 상태 선점, `ON CONFLICT`, HMAC을 설명한다.

## 2. 수단 비교: 무엇을 고르고 무엇을 버렸나

| 수단 | 어떻게 막나 | 장점 | 단점 | 채택 |
|---|---|---|---|---|
| **UNIQUE 제약** (+ `ON CONFLICT DO NOTHING`) | 같은 키의 두 번째 INSERT를 DB가 거절 | 가장 확실함. 서버가 여러 대여도 동작함 | "같다"의 기준(키)을 잘 정해야 함 | ✅ 이벤트 중복, 프로필 중복 |
| **조건부 UPDATE** (상태 선점) | `UPDATE ... WHERE status = '이전상태'` → 먼저 온 1건만 영향 행 1 | 락을 오래 잡지 않음, 코드 한 줄 | 결과(영향 행 수)를 반드시 확인해야 함 | ✅ 모든 상태 전이 |
| 비관적 락 (`SELECT ... FOR UPDATE`) | 먼저 읽은 쪽이 끝날 때까지 다른 쪽이 대기 | 직관적 | **외부 HTTP 호출 동안 락을 쥐고 있으면** 다른 요청이 줄줄이 대기함. 데드락 위험 | ❌ |
| 낙관적 락 (`@Version`) | 저장할 때 버전이 다르면 예외 | JPA 기본 기능 | 충돌 시 예외 처리·재시도 코드가 필요. "이미 처리됨"과 "충돌"을 구분하기 번거로움 | ❌ (조건부 UPDATE가 같은 일을 더 간단히 함) |
| 분산 락 (Redis 등) | 외부 저장소로 락 | 여러 서비스 간 조정 | 인프라 추가, 락 만료 시간 설계 필요 | ❌ 과함 |
| `synchronized` / 메모리 락 | JVM 안에서만 순서 보장 | 쉬움 | **서버가 2대면 무용지물**, 재시작하면 사라짐 | ❌ |

**1년차 말투 요약**: "처음엔 `synchronized`를 떠올렸는데 서버가 두 대면 소용없다는 걸 알았습니다. `SELECT FOR UPDATE`도 생각했지만, 락을 잡은 채로 PG를 호출하면 PG가 3초 늦을 때 다른 요청이 전부 3초씩 기다립니다. 결국 '같은 이벤트는 한 번만 저장된다'는 UNIQUE 제약과 '상태가 이전 값일 때만 바꾼다'는 조건부 UPDATE, 이 두 가지를 DB에 맡기는 쪽으로 정했습니다. 둘 다 SQL 한 문장이라 설명하기도 쉬웠습니다."

## 3. 결제 확정 처리 (D3·D4) — 승인 응답과 웹훅의 공통 경로

승인 API 응답, 웹훅, 대사 스케줄러는 **모두 같은 메서드** `PaymentConfirmService.confirm()`으로 들어온다. 경로가 하나여야 중복 처리 규칙도 하나가 된다.

```java
@Transactional
public ConfirmResult confirm(PgResult r, Signal signal) {
    // ① 이벤트 기록 = 중복 체크. 이미 같은 키가 있으면 0 반환
    int inserted = callbackLogRepository.insertIgnore(
        "PG", "PG:" + r.pgTid() + ":" + r.status(), r.rawPayload(), true);
    if (inserted == 0) return ConfirmResult.DUPLICATE;

    Payment p = paymentRepository.findByOrderNo(r.orderNo()) ...;   // 없으면 UNMATCHED 기록
    SimOrder o = ...;

    // ② 금액 검증: 통지 금액 ≠ 주문 금액이면 결제 완료로 처리하지 않음
    if (r.amount() != o.getAmount()) {
        callbackLogRepository.markResult(..., "AMOUNT_MISMATCH");
        return ConfirmResult.AMOUNT_MISMATCH;           // 주문은 PENDING 그대로, 어드민 이상 건에 노출
    }

    if (r.status() == FAILED) { paymentTransition(p, READY, FAILED); return FAILED; }

    // ③ 상태 선점: 결제 READY→APPROVED, 주문 PENDING→PAID
    paymentRepository.approveIf(p.getId(), r.pgTid());          // WHERE status='READY'
    boolean paid = transition.transit(o.getId(), PENDING, PAID, Actor.PG, signal, "결제 승인");
    if (!paid && o.isExpired()) {
        refundService.startAuto(o, "만료 후 도착한 승인 → 자동 취소");  // §06-7
        return LATE_APPROVAL;
    }
    if (paid) events.publishEvent(new OrderPaidEvent(o.getId()));    // 커밋 후 발급 시작
    return paid ? PROCESSED : ALREADY_PROCESSED;
}
```

### 왜 이렇게 하면 동시에 20개가 와도 1번만 처리되나
- 트랜잭션 A와 B가 **같은 `event_key`**로 동시에 INSERT하면, PostgreSQL은 B를 **A가 끝날 때까지 기다리게** 한다
  - A가 커밋하면 → B의 `ON CONFLICT DO NOTHING`이 0행을 반환 → B는 `DUPLICATE`로 종료
  - A가 실패(롤백)하면 → B의 INSERT가 성공 → B가 처리를 이어받음
- 즉 **"중복 체크"와 "처리"가 같은 트랜잭션**이라서, 처리 도중 실패하면 중복 기록도 같이 사라지고 다음 재전송이 정상 처리된다. 이것이 중복 기록을 별도 트랜잭션으로 먼저 커밋하지 않은 이유다
- 이중 안전장치로, 혹시 event_key가 다르게 들어오더라도(예: 승인 응답과 웹훅의 형식이 다름) **주문 `PENDING→PAID` 조건부 UPDATE**가 한 번만 성공한다

### PG 웹훅의 신뢰
모의 PG 웹훅에도 `X-Signature`(HMAC, PG 전용 비밀키)를 붙인다. 서명이 틀리면 공급사 콜백과 똑같이 거절한다. 그리고 **금액은 웹훅 본문을 믿지 않고 우리 DB의 주문 금액과 비교**한다.

## 4. event_key를 무엇으로 만드나 (부록 A-1)

> "중복 콜백을 막는 키는 무엇으로 만듭니까? 본문 해시입니까, 공급사가 준 ID입니까? 같은 이벤트가 내용만 조금 달라 다시 오면요?"

| 후보 | 문제 |
|---|---|
| 본문 전체 해시 | 재전송 때 `sentAt` 같은 필드가 한 글자만 달라도 **다른 이벤트로 취급** → 중복 처리됨 |
| 공급사가 주는 이벤트 ID | 가장 좋지만 이번 공급사 명세(부록 A)에는 이벤트 ID가 없음 |
| **업무 식별자 + 이벤트 종류** ✅ | `SUP:{supplierOrderNo}:ISSUED`, `SUP:{iccid}:INSTALLED`, `PG:{pgTid}:APPROVED` |

선택 이유: "한 공급사 주문에 대한 발급 완료 이벤트는 논리적으로 한 번뿐"이므로 **의미 기준**으로 키를 만들었다.

**내용이 조금 다른 같은 이벤트가 다시 오면?** 키가 같으므로 두 번째는 처리되지 않는다. 그런데 핵심 값이 다르면 문제다. 예를 들어 같은 supplierOrderNo인데 ICCID가 다르게 왔다면 공급사 쪽 오류일 수 있다. 그래서 중복으로 걸러진 콜백이라도 **이미 저장된 프로필의 ICCID와 비교**해서, 다르면 `CONFLICT`로 기록하고 어드민 이상 건에 노출한다. 자동으로 덮어쓰지 않는다. 사람이 판단할 일이라고 봤다.

## 5. 공급사 발급 콜백 처리 (D5·D6)

```
POST /api/webhooks/supplier
  1. 원문 바이트(raw body) 그대로 HMAC-SHA256 계산 → X-Signature와 고정 시간 비교
     실패 → callback_log(signature_ok=false, result=SIGNATURE_INVALID, event_key=NULL) 저장, 401 응답
  2. event_key INSERT ... ON CONFLICT DO NOTHING → 0행이면 200 응답(이미 처리됨)
  3. supplierOrderNo로 주문 찾기 → 없으면 §6
  4. sim_profile INSERT (order_id UNIQUE, iccid UNIQUE) ON CONFLICT DO NOTHING
  5. 주문 ISSUING → ISSUED 조건부 UPDATE
     0행이면: 이미 ISSUED → 무시 / ISSUE_FAILED·REFUNDING → LATE_AFTER_FAIL 기록 (04 §5)
  6. 200 응답
```

**순서가 뒤바뀌는 경우(D6)**: 예를 들어 `INSTALLED` 콜백이 `ISSUED` 콜백보다 먼저 올 수 있다.
- 설치 상태에는 순위가 있다: `ISSUED(1) < QR_VIEWED(2) < INSTALLED(3) < ACTIVE(4) < EXPIRED(5)`. 새 신호의 순위가 현재보다 **높을 때만** 반영한다. 늦게 도착한 옛날 신호는 `STALE_IGNORED`로 기록만 한다
- 프로필이 아직 없는데 설치 이벤트가 오면 버리지 않고 기록만 남긴다(`EARLY_EVENT`). 발급 직후 첫 상태 조회(1분 뒤)에서 공급사의 실제 상태로 맞춰진다. **콜백은 빠른 힌트, 조회는 사실 확인**이라는 원칙 덕분에 순서 문제를 복잡한 재정렬 로직 없이 해결했다(`07` §2)

## 6. 서명은 맞는데 DB에 없는 주문번호가 오면? (인터뷰 I5)

1. **서명이 맞다** = 진짜 공급사가 보냈다는 뜻이다. 공격은 아니다
2. 가능한 원인
   - (a) 우리가 공급사에 요청은 보냈는데 **supplierOrderNo를 저장하기 전에 서버가 죽었다** (`06` §5)
   - (b) 다른 환경(스테이징)의 주문이 섞였다
   - (c) 공급사 쪽 버그
3. 처리
   - 콜백 본문의 `orderNo`(우리가 요청할 때 넘긴 외부 참조)로 한 번 더 찾는다. (a)라면 여기서 찾아지므로 supplierOrderNo를 채우고 정상 처리한다
   - 그래도 없으면 `callback_log.result = UNMATCHED`로 원문을 저장하고 **200을 응답**한다. 4xx를 주면 공급사가 계속 재전송해서 로그가 쌓이기 때문이다. 대신 어드민 이상 건에 노출되어 사람이 확인한다
   - 프로필을 새로 만들거나 주문을 지어내지는 않는다

## 7. 운영자 동시 조치 (D8)

- 환불 버튼을 누르면 화면이 `requestKey`(UUID)를 만들어 보낸다 → `admin_action.request_key UNIQUE`가 **같은 클릭의 중복**을 막는다
- **서로 다른 두 운영자의 클릭**은 requestKey가 다르다. 이것은 주문 상태 선점(`ISSUED→REFUNDING` 조건부 UPDATE)이 막는다. 먼저 도착한 쪽만 1행을 얻고, 나머지는 "이미 다른 운영자가 처리 중입니다(처리자: admin-2)" 응답을 받는다
- 그래도 PG 취소는 한 번만 나가야 하므로 `refund_attempt`에 부분 유니크 `(payment_id) WHERE status IN ('PENDING','IN_PROGRESS')`를 하나 더 둔다
- 두 운영자의 시도는 성공이든 거절이든 모두 `admin_action`에 남는다. 누가 언제 무엇을 눌렀는지가 기록된다

## 9. 한계 (인터뷰에서 먼저 말할 것)

- `event_key`를 업무 식별자로 만들었기 때문에, 공급사가 **정말로 같은 종류의 이벤트를 두 번 보내야 하는 경우**(예: 재발급)를 구분하지 못한다. 그런 기능이 생기면 공급사 이벤트 ID가 필요하다
- **금액이 틀린 웹훅도 event_key를 차지한다.** 서명이 맞는(=진짜 PG가 보낸) 웹훅의 금액이 틀렸다면, 같은 pgTid로 오는 이후 통지도 처리되지 않고 어드민이 확인해야 한다. 진짜 PG가 금액을 다르게 말하는 것 자체가 사람이 봐야 할 사고라서 이렇게 두었다. 반면 **서명이 틀린 요청은 event_key를 NULL로 저장**하므로 위조 요청이 정상 키를 선점하는 공격은 통하지 않는다
- 웹훅 서명 비밀키 교체(rotation)는 고려하지 않았다
- 콜백 처리 중 DB가 느리면 공급사 쪽에서 타임아웃이 나서 재전송이 올 수 있다. 재전송은 멱등하게 처리되지만 부하가 늘 수 있다

# Part 1. 필수 답변 8개 질문 (2.4) — README에 그대로 옮길 것

## Q1. 왜 이 기술들을 골랐습니까? (필수)

**30초 답변**
> "백엔드는 써 본 적 있는 Java 17과 Spring Boot 3를 골랐습니다. Next.js가 처음이라 백엔드까지 새 기술을 쓰면 둘 다 설명을 못 할 것 같았습니다. ORM은 JPA를 쓰되, 중복 처리가 걸린 상태 변경은 네이티브 쿼리로 조건부 UPDATE를 직접 썼습니다. 비동기는 커밋 후 이벤트와 `@Async`로 바로 처리하고, 놓친 건 `@Scheduled`가 DB 상태를 보고 다시 처리하게 했습니다. DB는 회사에서 쓰고 `ON CONFLICT`와 부분 인덱스가 있는 PostgreSQL을 골랐고, 프론트는 공식 튜토리얼이 기준으로 삼는 App Router를 썼습니다. 배포는 서버가 잠들지 않는 AWS EC2와 RDS로 했습니다."

**왜 그렇게 했나** — 요약표 (상세 [02_기술선택_ADR](02_기술선택_ADR.md))
| 영역 | 선택 | 버린 것과 이유 |
|---|---|---|
| 라우터 | App Router | Pages Router: 현재 공식 기준이 아님 |
| 데이터 패칭 | Server Component fetch + TanStack Query 폴링 | useEffect 직접 구현: 정리·중복 방지를 직접 짜야 함 / SSE: 수 초짜리 대기에 과함 |
| ORM | JPA + 네이티브 조건부 쿼리 | MyBatis: 단순 CRUD까지 SQL / JPA setter 방식: 경쟁 상태 |
| 비동기 | AFTER_COMMIT + @Async + @Scheduled | Kafka: 무료 서버에 브로커 추가는 과함 / 스케줄러만: 느림 / @Async만: 서버 다운 시 유실 |
| DB | PostgreSQL | MySQL: 부분 유니크 인덱스 없음 / H2: 운영과 동작이 다름 |
| 마이그레이션 | Flyway | ddl-auto: 실행된 DDL이 안 보임 |
| 테스트 | Testcontainers | H2: 동시성 테스트가 거짓으로 통과할 수 있음 |
| 배포 | EC2 + RDS | Render 무료: 15분 후 잠들어 스케줄러 정지 |
| PR 화면 캡처 | Playwright MCP | 수동 캡처: before·after 조건이 매번 다름 |

**문서·코드 위치**: `docs/02`, `backend/build.gradle`, `frontend/package.json`

**예상 꼬리질문**
- Q: 다른 선택지와 비교해 본 적이 있나요? → A: "MyBatis와 비교했습니다. SQL이 다 보인다는 장점이 있지만 필요한 건 상태 변경 쿼리 몇 개뿐이라, JPA의 `@Query(nativeQuery=true)`로 충분하다고 판단했습니다."
- Q: 어드민 주문 목록은 JPA가 아니던데요? → A: "네, 어드민 조회만 `NamedParameterJdbcTemplate`으로 SQL을 직접 썼습니다. 주문·최신 결제·프로필 세 테이블을 묶고 조건을 값이 있을 때만 거는데, 이 테이블들은 기능이 달라 JPA 연관관계가 없습니다. Specification으로 하면 서브쿼리를 Criteria로 짜야 해서 제가 SQL을 설명하기 어려웠습니다. 쓰기는 JPA, 여러 테이블 읽기는 SQL로 나눴고, 조건 값은 꼭 파라미터로 넘겨서 SQL 인젝션을 막았습니다." (ADR-16, `AdminOrderQueryRepository`)
- Q: Kafka를 안 쓴 이유는? → A: "작업 목록 역할을 DB의 주문 상태가 하고 있어서, 이 규모에서는 스케줄러로 충분하다고 봤습니다. 서버가 여러 대가 되고 작업량이 많아지면 큐가 필요해질 것 같습니다."
- Q: TanStack Query를 왜 추가했나요? → A: "폴링을 직접 짜면 화면을 떠나도 요청이 계속 나가거나 중복 요청이 생길 수 있었습니다. 완료되면 멈추는 조건도 한 줄로 쓸 수 있어서 골랐습니다."

**한계 인정**
> "Next.js는 처음이라 캐시 동작을 완전히 이해하지 못해서 결제 관련 조회는 전부 캐시를 껐습니다. 성능상 최적은 아니라는 걸 알고 있습니다."

**스스로 점검**
- [ ] 각 선택마다 버린 대안 하나와 그 이유를 말할 수 있다
- [ ] "익숙해서" 고른 것과 "처음 써 본" 것을 구분해서 말할 수 있다

## Q2. 결제부터 발급까지 주문 상태를 어떻게 설계했습니까?

**30초 답변**
> "상태를 주문, 결제, 설치 세 갈래로 나눴습니다. 주문은 PENDING → PAID → ISSUING → ISSUED로 가고, 실패하면 ISSUE_FAILED → REFUNDING → REFUNDED, 환불도 실패하면 REFUND_FAILED가 됩니다. 결제는 됐는데 발급이 안 된 주문은 PAID나 ISSUING에 있고, 정상이면 공급사 콜백이, 콜백이 안 오면 30초마다 도는 스케줄러가 최대 3번 재요청해서 끝냅니다. 그래도 안 되면 자동 환불되고, 환불도 실패하면 운영자 이상 건 화면에 남습니다. 발급은 브라우저가 아니라 서버가 시작하기 때문에 결제 직후 창을 닫아도 끝까지 진행됩니다."

**왜 그렇게 했나**
- **모든 비최종 상태에 "끝내는 주체"를 지정**했다. 주체가 없는 상태가 있으면 주문이 영원히 멈추기 때문이다

| 상태 | 정상 종료 | 비정상 종료 |
|---|---|---|
| PENDING | 결제 확정(PG) | 10분 후 만료(스케줄러) |
| PAID | 커밋 후 이벤트 | 30초 넘으면 스케줄러 |
| ISSUING | 공급사 콜백 | 2분 타임아웃 재시도 ×3 → ISSUE_FAILED |
| ISSUE_FAILED | 자동 환불 | 운영자 발급 재시도 |
| REFUNDING | PG 취소 성공 | 재시도 ×3 → REFUND_FAILED |
| REFUND_FAILED | 운영자 | (이상 건에 계속 노출) |

- 상태를 하나로 합치지 않은 이유: 부분 취소, QR 열람→설치→개통이 각각 따로 움직여서 하나에 담으면 조합이 폭발한다
- 클라이언트가 "발급해 줘"를 호출하는 구조를 **처음부터 택하지 않았다**

**문서·코드 위치**: [04_상태설계](04_상태설계.md), `OrderStatus.canTransitTo()`, `OrderService.markPaid`, `StatusHistoryService`, `IssueService.onOrderPaid`, `IssueScheduler`(PAID 방치 안전망), 재시도 스케줄러(보완 단계)

**예상 꼬리질문**
- Q: 왜 바로 환불하지 않고 3번 재시도하나요? → A: "공급사 장애는 대부분 일시적이고, 사용자는 SIM을 원해서 결제했으니까요. 대신 약 6분 안에 결론을 내도록 상한을 뒀습니다."
- Q: 상태 전이를 잘못하는 걸 어떻게 막나요? → A: "허용 전이표를 enum에 코드로 넣었고, 상태는 그 기능 Service의 전이 메서드에서만 조건부 UPDATE로 바꿉니다. 바뀌었을 때만 같은 트랜잭션에서 이력이 남습니다. 처음엔 상태 전이 서비스 하나에 모았는데, 그 서비스가 다른 기능의 Repository를 써야 해서 기능별로 나누고 이력 저장만 history 기능으로 뺐습니다."
- Q: 환불 처리 후에 발급 콜백이 오면? → A: "프로필을 붙이지 않고 LATE_AFTER_FAIL로 기록해 어드민에 보여 줍니다. 원래는 공급사에 프로필 회수를 요청해야 하는데 그건 구현하지 못했습니다."

**한계 인정**
> "환불 시작 후에 늦게 온 발급 콜백의 프로필 회수는 구현하지 않았습니다. 지금은 운영자가 보고 처리해야 합니다."

**스스로 점검**
- [ ] 상태 전이도를 보지 않고 화이트보드에 그릴 수 있다
- [ ] 각 상태를 누가 끝내는지 말할 수 있다
- [ ] "브라우저를 닫으면?"에 서버의 어떤 코드가 발급을 시작하는지 가리킬 수 있다

## Q3. 중복 처리를 어떻게 막았고, 어떻게 증명했습니까?

**30초 답변**
> "두 가지를 DB에 맡겼습니다. 첫째, 받은 이벤트를 `callback_log`에 event_key UNIQUE로 저장하면서 `ON CONFLICT DO NOTHING`을 써서 같은 통지는 한 번만 기록되게 했습니다. 둘째, 상태 변경은 '상태가 PENDING일 때만 PAID로'라는 조건부 UPDATE로 해서, 동시에 와도 한 건만 바뀝니다. 프로필은 `order_id`에 UNIQUE를 걸어 두 번 붙을 수 없게 했습니다. 증명은 ExecutorService와 CountDownLatch로 같은 웹훅 20개를 동시에 보내서 결제 1건, 이력 1줄, 발급 요청 1번인지 세는 테스트로 했습니다."

**왜 그렇게 했나**
| 수단 | 판단 |
|---|---|
| UNIQUE + `ON CONFLICT` | ✅ 서버가 여러 대여도 동작, 가장 확실 |
| 조건부 UPDATE | ✅ 락을 오래 잡지 않음 |
| `SELECT FOR UPDATE` | ❌ 락을 쥔 채 외부 호출 시 대기 폭증 |
| `@Version` | ❌ 원리는 같지만 예외·재시도 코드 필요 |
| `synchronized` | ❌ 서버 2대면 무용지물 |
| Redis 락 | ❌ 인프라 추가 |

**예상 꼬리질문**

## Q4. 트랜잭션 경계는 어디에 그었습니까?

**30초 답변**
> "PG와 공급사 호출은 전부 트랜잭션 밖입니다. 보내기 전에 '보낸다'는 상태(결제 READY, 주문 ISSUING)를 먼저 커밋하고, 호출한 뒤 결과는 새 트랜잭션에 저장합니다. 안에 두면 외부가 느릴 때 DB 커넥션을 잡고 있게 되고, 승인 후에 롤백되면 돈은 나갔는데 기록이 사라지기 때문입니다. 공급사가 접수했는데 우리 저장이 실패하면, 공급사에 우리 주문번호를 멱등키로 넘겼기 때문에 재요청해도 같은 공급사 주문번호를 돌려받습니다. 결제 버튼 연타와 타임아웃 후 재시도는 둘 다 화면이 결제 페이지 진입 시 한 번 만든 Idempotency-Key로 막습니다."

**왜 그렇게 했나**
- 트랜잭션 안에서 외부를 호출하면 생기는 문제: ① 커넥션·락 점유 ② **롤백으로 흔적이 사라짐** ③ "보냈는지" 기록이 없음
- 연타와 재시도는 서버 입장에서 구분할 수 없다. 둘 다 "같은 의도의 요청"이므로 같은 키로 같은 결과를 준다

| 상황 | 키 |
|---|---|
| 버튼 연타 / 타임아웃 재시도 | `Idempotency-Key` → `payment.idempotency_key UNIQUE` |
| 다른 탭에서 동시 결제 | `payment (order_id) WHERE status='READY'` 부분 유니크 |
| 우리 → PG 재요청 | `paymentId` |
| 우리 → 공급사 재요청 | `orderNo` |
| PG 취소 재시도 | `refund_attempt.request_key` |

**문서·코드 위치**: [06_트랜잭션_경계](06_트랜잭션_경계.md), [L2 §2](learn/L2_Spring_비동기_스케줄러.md), `PaymentService.pay`(TransactionTemplate), `PaymentConfirmService`

**예상 꼬리질문**
- Q: 같은 클래스에서 `@Transactional` 메서드를 부르면? → A: "프록시를 거치지 않아서 트랜잭션이 안 걸립니다. 그래서 트랜잭션이 필요한 부분을 별도 클래스로 뺐습니다."
- Q: 멱등키를 클릭할 때마다 만들면? → A: "연타하면 키가 달라져서 결제가 두 번 생깁니다. 그래서 페이지에 들어올 때 한 번만 만듭니다."
- Q: 커밋 직후 서버가 죽어서 이벤트가 유실되면? → A: "주문이 PAID로 남아 있으니 스케줄러가 30초 안에 찾아서 발급을 요청합니다."

**한계 인정**
> "PG와 공급사가 우리 멱등키를 지원한다고 가정했고, 모의 시스템이라 직접 그렇게 만들었습니다. 실제 업체가 지원하지 않으면 재요청 전에 조회 API로 먼저 확인하는 방식으로 바꿔야 합니다."

**스스로 점검**
- [ ] tx1 → HTTP → tx2 순서를 코드에서 가리킬 수 있다
- [ ] "트랜잭션 안이 더 안전하지 않나요?"에 반박할 수 있다

## Q5. "이 사용자가 SIM을 설치했다"를 무엇으로 판단합니까?

**30초 답변**
> "설치는 사용자 폰에서 일어나서 직접 볼 수 없습니다. 우리가 직접 아는 건 QR을 열어 봤다는 것뿐이라 그건 설치 근거로 안 썼습니다. 공급사 콜백은 빠르지만 빠질 수 있어서 오면 바로 반영만 하고, 빠진 건 주기적인 상태 조회로 메웠습니다. 조회는 모든 SIM을 매분 하지 않고, QR을 방금 열어 본 SIM은 2분, 여행 시작일 근처의 미설치 SIM은 10분, 나머지는 6시간처럼 곧 바뀔 것만 자주 봅니다. 환불 버튼을 누른 순간에는 무조건 공급사에 한 번 더 물어보고 판단합니다."

**왜 그렇게 했나**
| 신호 | 속도 | 확실성 | 사용 |
|---|---|---|---|
| QR 열람 | 즉시 | 기록은 확실, 설치 증거 아님 | 참고, 폴링 주기 단축 |
| 공급사 콜백 | 빠름 | 진짜지만 누락 가능 | 오면 반영 |
| 공급사 상태 조회 | 느림 | 그 순간의 사실 | 누락 보정, 환불 직전 필수 |

- 상태는 **앞으로만** 간다. 늦게 온 옛날 신호를 무시할 수 있고, 환불 판단이 안전한 쪽으로 기운다
- 신호가 틀렸을 때 사용자는 "마지막 확인: N분 전"과 [다시 확인] 버튼을 본다. 운영자는 타임라인에서 **신호 출처와 발생/기록 시각 두 개**를 보고, 모순은 `SIGNAL_CONFLICT` 이상 건으로 본다

**지금 구현된 범위 (기본 흐름)**: QR 열람 기록, 공급사 상태 조회로 INSTALLED·ACTIVE 반영(앞으로만), 개통 시 만료일 계산, 개통 전 SIM 전체를 1분마다 조회, 사용자 [다시 확인], 만료 시각이 지나면 EXPIRED. **아직 없는 것**: 공급사 설치 콜백 수신, SIM별로 조회 주기를 다르게 하는 선택적 폴링(지금은 미설치 SIM도 기간 제한 없이 매분 조회), 조회 연속 실패를 이상 건으로 노출, DELETED, 환불 직전 동기 조회(보완 단계). 인터뷰 때까지 못 만들면 "지금은 1분마다 전부 조회하고, 위 표처럼 나누는 게 다음 단계"라고 그대로 말한다

**문서·코드 위치**: [07_설치추적_만료](07_설치추적_만료.md), `InstallTrackingService`(viewQr·refresh·expireDue), `InstallPollingScheduler`, `InstallStatus.canMoveTo()`, `ExpiryCalculator`, `RefundEligibilityService`(보완 단계)

**예상 꼬리질문**
- Q: 콜백은 INSTALLED였는데 조회는 RELEASED면? → A: "되돌리지 않고 SIGNAL_CONFLICT로 남겨 운영자가 보게 합니다. 환불 쪽으로는 보수적으로 판단하는 게 맞다고 봤습니다."
- Q: 조회 API가 장애면 환불은? → A: "보류하고 운영자에게 넘깁니다. 모를 때 돈을 내보내는 쪽으로 추측하지 않습니다."

**한계 인정**
> "폴링 주기 숫자는 근거 데이터 없이 정한 초기값입니다. 실제로는 콜백 누락률과 공급사 rate limit을 보고 조정해야 합니다."

**스스로 점검**
- [ ] 세 신호의 신뢰도 차이를 예시와 함께 말할 수 있다
- [ ] 폴링 대상을 고르는 기준을 3개 이상 말할 수 있다

## Q6. 어드민과 사용자 화면에서 서버와 클라이언트의 경계를 어디에 그었습니까?

**30초 답변**
> "'처음 보여 줄 데이터는 서버, 사용자가 누르거나 시간이 지나며 바뀌는 건 브라우저'라는 기준으로 나눴습니다. 페이지는 전부 Server Component에서 API를 호출해 완성된 HTML로 보내고, 주문 폼, 결제 버튼, 발급 대기 폴링, 설치 코드 보기, 어드민 필터 폼과 새로고침 버튼, 지금 화면을 표시하고 휴대폰에서 접히는 왼쪽 메뉴만 `'use client'`로 만들었습니다. 발급 대기 화면은 TanStack Query로 2초마다 다시 묻고 최종 상태가 되거나 5분이 지나면 멈춥니다. 어드민 필터와 페이지는 URL 쿼리에 담아서 페이지(Server)가 URL을 읽고 조회합니다. 서버가 응답에 조회 시각(fetchedAt)을 넣고 화면이 '12초 전 데이터'처럼 보여 주며, [새로고침]이나 10초 자동 새로고침은 `router.refresh()`로 페이지를 서버에서 다시 그립니다. 운영자 조치 버튼은 보완 단계에서 만들고, 오래된 화면을 보고 눌러도 서버가 최신 상태로 다시 판단하게 할 계획입니다."

**왜 그렇게 했나**
- 폴링 vs SSE: 발급은 수 초면 끝나서 2~5번 묻고 끝난다. SSE는 연결 유지와 프록시 설정이 필요해 이득이 적다
- 경계를 아래로 내려서 브라우저로 가는 JS를 줄이고 첫 화면이 비어 있지 않게 했다
- 결제 상태는 `cache: 'no-store'`로 캐시를 껐다
- 대기 중에도 할 수 있는 일: "창을 닫아도 된다" 안내, [내 SIM에서 나중에 확인], 설치 방법 안내

**문서·코드 위치**: [08_프론트_경계](08_프론트_경계.md) §7(화면별 동작 표), [프론트 설계 기준](../.claude/skills/nextjs-architecture/ARCHITECTURE.md), [L1](learn/L1_Nextjs_기초.md), `features/order/components/IssueStatusPoller.tsx`, `features/admin/components/AdminFilters.tsx`·`RefreshControls.tsx`, `components/FreshnessBadge.tsx`

**예상 꼬리질문**
- Q: Server Component와 Client Component의 차이는? → A: "Server Component는 서버에서 실행돼 HTML로 오고 JS가 브라우저로 안 갑니다. 대신 useState나 onClick을 못 씁니다. Client Component는 브라우저에서 동작해 클릭과 타이머를 처리합니다."
- Q: 어드민 필터를 왜 `useState`가 아니라 URL에 두었나요? → A: "새로고침하거나 링크를 공유해도 같은 화면이 나오게 하려고요. 페이지가 서버에서 URL만 보고 조회하면 되니까 필터 폼은 URL을 바꾸는 일만 합니다. 폼의 `useState`는 [조회]를 누르기 전에 고르는 중인 값만 들고 있습니다."
- Q: 사용 기간 막대는 왜 서버에서 지금 시각을 쓰나요? → A: "'5일 17시간 남음'처럼 시간 단위 값이라 새로고침할 때만 바뀌어도 충분합니다. 서버에서 그린 순간의 시각으로 한 번 계산하면 화면이 뜰 때 숫자가 바뀌며 깜빡이지 않습니다. 만료 시각 자체는 백엔드가 개통 시각 + 일수 × 24시간으로 계산해 준 값을 그대로 쓰고, 화면은 지난 비율만 계산합니다. 'N초 전 데이터'처럼 1초마다 바뀌는 것만 브라우저에서 계산합니다."
- Q: 왼쪽 메뉴의 아이디는 어떻게 화면에 들어가나요? → A: "모든 화면의 틀(layout)이 서버에서 쿠키를 읽어 아이디 입력칸에 넘깁니다. 저장하면 쿠키를 바꾸고 `router.refresh()`로 서버 부분을 다시 그려서 메뉴와 화면이 새 아이디로 바뀝니다."
- Q: `router.refresh()`는 무엇을 하나요? → A: "페이지 전체를 새로 받지 않고 그 페이지의 Server Component만 서버에서 다시 실행해서 바뀐 부분을 갈아 끼웁니다. 그래서 버튼이 데이터를 직접 고치지 않아도 화면이 항상 서버 데이터 기준이 됩니다."
- Q: 페이지 전체를 `'use client'`로 하면 안 되나요? → A: "되긴 하지만 첫 화면을 브라우저에서 다시 불러와야 해서 로딩이 생기고 JS가 커집니다."
- Q: "N초 전"을 서버에서 계산하면? → A: "서버 시각과 브라우저 시각이 달라 하이드레이션 경고가 나고, 시간이 지나도 숫자가 안 바뀝니다. 그래서 클라이언트에서 1초마다 계산합니다."

**한계 인정**
> "대기 화면 사용자가 많아지면 2초 폴링 요청이 쌓입니다. 간격을 점점 늘리거나 SSE로 바꾸는 게 다음 단계입니다."

**스스로 점검**
- [ ] 화면 하나를 골라 어디가 서버이고 어디가 클라이언트인지 그 이유와 함께 말할 수 있다
- [ ] 폴링이 멈추는 조건을 코드에서 가리킬 수 있다
